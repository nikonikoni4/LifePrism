# 数据备份与恢复

> **检索标签**：备份, 恢复, backup, restore, 文档备份, 数据库备份, 数据丢失, 紧急恢复, sync_conflict, 预恢复快照, pre_restore, lifewatch_ai.db, SQLite Online Backup, APScheduler, BackupService, ScheduleService, 平铺备份, 备份保留, 3 份, 30 天, file_sync_state, CONFLICT, ReadFileTool, Agent 可读

> **本文档面向 Agent 可读**：未来 Agent 可通过 `ReadFileTool` 读取本文档以指导用户手工恢复操作。文档结构使用清晰的 Markdown 二级标题（`##`）划分章节，便于 ReadFileTool 解析与定位。

## 1. 备份位置说明

所有备份文件统一存放在 LifePrism 数据目录下的 `backups/` 子目录：

```
{lifeprism_data_path}/backups/
```

- `lifeprism_data_path`：LifePrism 本地数据根目录（启动时由 `settings.lifeprism_data_path` 决定）
- 该目录由 `BackupService` 在首次备份时自动创建，无需用户手动建目录
- 备份按对象类型分两个子目录：
  - `backups/docs/`：文档快照（详见第 2 章）
  - `backups/db/`：数据库快照（详见第 3 章）
- 备份仅在本地 `full` 模式下执行；云端 `agent_only` 与 `web_demo` 模式**不执行备份**（由 `BackupService._check_run_mode()` 守卫）

### 备份调度概览

| 备份对象 | 频率 | 触发时间（本地时区） | 保留份数 | 调度方式 |
|---------|------|--------------------|---------|---------|
| **文档** | 每天 1 次 | 03:00 | 最新 3 份 | APScheduler cron `0 3 * * *` |
| **数据库** | 每 8 小时 1 次 | 00:00 / 08:00 / 16:00 | 最新 3 份 | APScheduler cron `0 0,8,16 * * *` |

调度由 `ScheduleService`（基于 APScheduler 的 `AsyncIOScheduler`）注册并触发，复用本地时区（`pytz.timezone(get_user_timezone())`）。

## 2. 文档备份结构说明

文档备份位于 `backups/docs/{timestamp}/`，每个时间戳对应一次完整快照：

```
{lifeprism_data_path}/backups/docs/
├── 2026-07-17T03-00-00/         ← 文档快照（目录名为本地时区备份时间）
│   ├── session/                  # 聊天会话 JSONL
│   ├── diary/                    # 日记 Markdown
│   ├── agent/                    # Agent 身份、记忆、配置
│   ├── user/                     # 用户级数据
│   └── plan/                     # 计划文档（仅备份，不加入同步范围）
├── 2026-07-16T03-00-00/
└── 2026-07-15T03-00-00/
```

### 子目录说明（5 个）

| 子目录 | 内容 | 来源 |
|--------|------|------|
| `session/` | 聊天会话 JSONL | `lifeprism/backup/constants.py: BACKUP_DIRS` |
| `diary/` | 日记 Markdown | 同上 |
| `agent/` | Agent 身份、记忆、配置 | 同上（排除 `chat_history.json` 和 `bootstrap.md`） |
| `user/` | 用户级数据 | 同上（排除 `chat_history.json` 和 `bootstrap.md`） |
| `plan/` | 计划文档 | 同上（仅备份，不加入同步范围） |

### 排除文件

以下文件名在备份时被排除（与同步 `EXCLUDED_FILENAMES` 保持一致）：

- `chat_history.json`：由 dreaming task 写入，云端无 dreaming 不变更
- `bootstrap.md`：Agent 启动引导配置，由模板初始化，各端独立维护

### 时间戳格式

- 格式：`YYYY-MM-DDTHH-MM-SS`（本地时区，冒号 `:` 替换为短横 `-` 以兼容 Windows 文件系统）
- 示例：`2026-07-17T03-00-00` 表示本地时区 2026 年 7 月 17 日 03:00:00 的备份

### 平铺存储（非 zip 压缩）

文档备份采用**平铺存储**而非 zip 压缩：

- 文件管理器可直接打开查看内容
- 单文件恢复只需复制，无需解压
- LifePrism 数据量小（文档几 MB），无压缩需求

## 3. 数据库备份结构说明

数据库备份位于 `backups/db/`，每个备份是独立的 SQLite `.db` 文件：

```
{lifeprism_data_path}/backups/db/
├── lifewatch_ai-2026-07-17T08-00-00.db    ← SQLite Online Backup 产物
├── lifewatch_ai-2026-07-17T16-00-00.db
└── lifewatch_ai-2026-07-18T00-00-00.db
```

### 文件命名规则

```
lifewatch_ai-{timestamp}.db
```

- `lifewatch_ai`：源数据库文件名 stem（来自 `dataset/lifewatch_ai.db`）
- `{timestamp}`：本地时区时间戳，格式同文档备份
- 示例：`lifewatch_ai-2026-07-17T08-00-00.db`

### 备份范围

- **全量备份**：备份 `dataset/lifewatch_ai.db` 的所有表（含 `file_sync_state`、本地产能表、配置表等）
- 与同步的 `SYNC_TABLES`（31 张表子集）**不同**，备份是整库全量
- 已弃用的 `chat_history.db` **不在备份范围**

### 备份方式：SQLite Online Backup API

使用 SQLite 内置的 Online Backup API（`sqlite3.Connection.backup(target)`）：

- **在线拷贝**：不阻塞业务读写（生产环境可继续写入）
- **原子性**：备份过程原子，不会产生半截损坏文件
- **可读性**：产物是普通 `.db` 文件，可用 DB Browser for SQLite 直接打开

### 完整性校验

每个数据库备份生成后立即执行 `PRAGMA integrity_check`：

- 返回 `ok` → 校验通过，保留备份
- 返回非 `ok` 或异常 → **删除损坏备份 + 记录 ERROR 日志**

## 4. 文档恢复操作步骤

### 场景 A：恢复单个文件

例如，误删或被同步破坏了 `agent/behavior.md`，希望恢复到 2026-07-17 03:00 的版本。

**步骤**：

1. **强烈建议先备份当前数据**（详见第 6 章）
2. **暂停 `sync_client`**（避免恢复过程中同步覆盖）：
   - 退出 LifePrism 桌面应用，或在设置中暂停同步
3. **定位目标备份**：打开 `{lifeprism_data_path}/backups/docs/`，按时间戳选择最近的备份目录
4. **复制单个文件覆盖本地**：

   PowerShell 示例：

   ```powershell
   # 源：备份目录中的文件
   $src = "{lifeprism_data_path}\backups\docs\2026-07-17T03-00-00\agent\behavior.md"
   # 目标：本地数据目录中的文件
   $dst = "{lifeprism_data_path}\agent\behavior.md"
   Copy-Item -Path $src -Destination $dst -Force
   ```

5. **重启 LifePrism 服务**（让 Agent 重新加载文档）
6. **恢复 `sync_client`**（确认无误后再开启同步，下次同步行为详见第 7 章）

### 场景 B：恢复整个时间戳目录

例如，整个 `agent/` 目录被破坏，希望恢复到某个时间点的全部文档。

**步骤**：

1. **强烈建议先备份当前数据**（详见第 6 章）
2. **暂停 `sync_client`**
3. **选择目标备份时间戳**，例如 `2026-07-17T03-00-00/`
4. **整个目录覆盖到 `{lifeprism_data_path}/`**：

   PowerShell 示例（恢复整个文档快照）：

   ```powershell
   # 源：备份目录
   $src = "{lifeprism_data_path}\backups\docs\2026-07-17T03-00-00\*"
   # 目标：本地数据目录
   $dst = "{lifeprism_data_path}\"
   Copy-Item -Path $src -Destination $dst -Recurse -Force
   ```

   注意保留目录结构（`session/`、`diary/`、`agent/`、`user/`、`plan/`）。

5. **重启 LifePrism 服务**
6. **恢复 `sync_client`**

### 文档恢复不停服

文档恢复**不需要关闭 LifePrism 服务**，但需要**暂停 `sync_client`**：

- 文档恢复期间，如果 `sync_client` 正在运行，可能将本地旧状态 push 到云端，覆盖云端版本
- 暂停 `sync_client` 后，本地恢复完成、确认无误，再恢复同步

## 5. 数据库恢复操作步骤

### ⚠️ 重要警告：数据库恢复必须停服

**数据库恢复必须停止 LifePrism 服务**，否则 SQLite 文件被覆盖时会损坏（SQLite 文件被覆盖时不能有连接）。

### 步骤

1. **关闭 LifePrism 服务**：
   - 完全退出 LifePrism 桌面应用
   - 确认没有 `python` / `lifeprism` 进程在运行

   PowerShell 示例（检查并停止进程）：

   ```powershell
   # 检查是否还有 lifeprism 进程
   Get-Process | Where-Object {$_.Name -like "*lifeprism*" -or $_.Name -like "*python*"} | Format-Table Name, Id
   # 如有，调用 Stop-Process -Id <PID> 停止
   ```

2. **强烈建议先备份当前数据库**（详见第 6 章）

3. **选择目标备份**：打开 `{lifeprism_data_path}/backups/db/`，选择最近的 `.db` 文件

4. **替换主数据库**：

   PowerShell 示例：

   ```powershell
   # 源：备份数据库
   $src = "{lifeprism_data_path}\backups\db\lifewatch_ai-2026-07-17T16-00-00.db"
   # 目标：主数据库
   $dst = "{lifeprism_data_path}\dataset\lifewatch_ai.db"
   Copy-Item -Path $src -Destination $dst -Force
   ```

5. **重启 LifePrism 服务**

6. **验证恢复**：
   - 打开应用，检查心情记录、日记、习惯打卡等数据是否正常显示
   - 如恢复的是几小时前的备份，期间产生的数据（聊天、心情记录）会丢失

### 数据库恢复与文档恢复的差异

| 项目 | 文档恢复 | 数据库恢复 |
|------|---------|----------|
| 是否需要停服 | ❌ 不需要 | ✅ **必须停服** |
| 是否需要暂停 sync_client | ✅ 需要 | ❌ 不需要（已停服） |
| 是否需要重启服务 | ✅ 推荐（重新加载文档） | ✅ 必须 |
| 是否影响 file_sync_state | ✅ 触发 CONFLICT（详见第 7 章） | ✅ 整库覆盖，状态以备份为准 |

## 6. 恢复前手动备份建议

### 强烈建议：恢复前先备份当前数据

**强烈建议**在恢复操作前，先将当前（即使已损坏）的数据复制到 `backups/pre_restore-{当前时间}/`，作为"预恢复快照"。

理由：
- 恢复操作不可逆，如果恢复后反悔，需要能回退到恢复前的状态
- 当前数据即使看起来已损坏，也可能包含尚未备份的最新内容
- 系统不提供自动 pre_restore 快照机制（决策依据：用户手工恢复时自行决定是否先备份当前状态）

### 预恢复备份目录命名

```
{lifeprism_data_path}/backups/pre_restore-{YYYY-MM-DDTHH-MM-SS}/
```

- 与系统自动备份的 `backups/docs/{timestamp}/` 平级
- `{YYYY-MM-DDTHH-MM-SS}` 为本地时区当前时间戳
- 不受"保留 3 份"策略影响（系统只清理 `backups/docs/` 和 `backups/db/` 下的旧备份，不清理 `pre_restore-*`）

### 预恢复备份操作

#### 文档预恢复备份

PowerShell 示例：

```powershell
# 当前时间戳
$ts = Get-Date -Format "yyyy-MM-ddTHH-mm-ss"
# 预恢复备份目录
$preRestoreDir = "{lifeprism_data_path}\backups\pre_restore-$ts"
New-Item -ItemType Directory -Path $preRestoreDir -Force

# 复制所有 BACKUP_DIRS（session/diary/agent/user/plan）
foreach ($subdir in @("session", "diary", "agent", "user", "plan")) {
    $src = "{lifeprism_data_path}\$subdir"
    if (Test-Path $src) {
        Copy-Item -Path $src -Destination $preRestoreDir -Recurse -Force
    }
}
```

#### 数据库预恢复备份

PowerShell 示例：

```powershell
$ts = Get-Date -Format "yyyy-MM-ddTHH-mm-ss"
$src = "{lifeprism_data_path}\dataset\lifewatch_ai.db"
$dst = "{lifeprism_data_path}\backups\pre_restore-$ts.db"
Copy-Item -Path $src -Destination $dst -Force
```

### 何时可以跳过预恢复备份

以下情况可以跳过预恢复备份：
- 当前数据完全损坏，无可恢复内容
- 已经在 `backups/` 中有刚生成的完整备份
- 用户明确接受"恢复后无法回退"的风险

## 7. 恢复后对 file_sync_state 的影响

### 文档恢复后：下次同步触发 CONFLICT（预期行为）

文档恢复后，`file_sync_state` 表中记录的 hash 与恢复后文件的实际 hash 不匹配：

| 字段 | 恢复前 | 恢复后 |
|------|--------|--------|
| `parent_hash` | 恢复前的状态 | 仍为恢复前的状态 |
| `current_hash` | 恢复前的文件 hash | **恢复后的文件 hash**（变化） |

**下次同步会触发 CONFLICT 状态**（`parent_hash != current_hash`）：

- 这是**预期行为**，不是 bug
- 走 diff3 + LLM 辅助合并流程
- 用户需在 Agent 对话中确认合并策略，或接受 diff3 自动合并结果

### 数据库恢复后：file_sync_state 整库覆盖

数据库恢复是**整库覆盖**，包括 `file_sync_state` 表本身：

- `file_sync_state` 表内容变为备份时的状态
- 下次同步以恢复后的 `file_sync_state` 为基准
- 如与云端有差异，会走 diff3 + LLM 辅助合并流程

### 恢复后建议

1. **观察下次同步日志**：
   - 查看 `{lifeprism_data_path}/debug_logs/sync.log`
   - 搜索 `CONFLICT` 关键词，确认哪些文件触发了冲突
2. **如有冲突未解决**：
   - 检查 `sync_conflict/` 目录（详见第 8 章）
   - 在 Agent 对话中处理冲突，或参考第 9 章 FAQ
3. **不要立即再次恢复**：
   - 让同步完成一轮，避免状态反复

## 8. sync_conflict/ 目录说明

### 目录用途

`sync_conflict/` 目录用于存放**同步冲突备份**：

- 当单个冲突块 LLM 重试 3 次都失败时，该冲突块降级为 `keep_ours`（保留本地版本），其他冲突块继续处理。仅当 base 内容无法获取时，整个文件降级为 LWW（保留本地版本）。冲突备份对所有进入冲突解决流程的文件都会执行，不限于降级场景。
- 此时**本地版本和云端版本都会被备份**到 `sync_conflict/{timestamp}/`
- 用户可对比本地与云端差异，判断 `keep_ours` 是否正确

### 目录结构

```
{lifeprism_data_path}/sync_conflict/
└── 20260717_154500/                          ← 冲突时间戳目录
    ├── agent__behavior.md.local.md           ← 本地版本（路径用 __ 分隔）
    └── agent__behavior.md.remote.md          ← 云端版本
```

### 与 backups/ 的区别

| 目录 | 用途 | 触发时机 | 保留期 |
|------|------|---------|--------|
| `backups/docs/` | 定时全量备份 | 每天 03:00 自动 | 保留最新 3 份 |
| `backups/db/` | 定时全量备份 | 每 8 小时自动 | 保留最新 3 份 |
| `backups/pre_restore-{ts}/` | 恢复前手动快照 | 用户手工触发 | 不自动清理 |
| `sync_conflict/{ts}/` | 冲突场景双版本备份 | 冲突降级时自动 | **保留 30 天** |

### 保留 30 天策略

- `sync_conflict/` 下的子目录按时间戳命名
- 超过 30 天的子目录会被自动清理
- 清理由 `backup_conflict_versions` 函数内联触发（每次冲突备份时顺带检查并清理过期目录，不依赖调度器定时任务）

### 如何从 sync_conflict/ 恢复某个冲突版本

详见第 9 章 FAQ Q5。

## 9. 常见问题（FAQ）

### Q1：如何恢复某个特定日记文件？

**场景**：误删了 `diary/2026-07-17.md`，希望从备份恢复。

**步骤**：

1. 暂停 `sync_client`
2. 定位备份：`{lifeprism_data_path}/backups/docs/2026-07-17T03-00-00/diary/2026-07-17.md`
3. 复制到本地：

   ```powershell
   $src = "{lifeprism_data_path}\backups\docs\2026-07-17T03-00-00\diary\2026-07-17.md"
   $dst = "{lifeprism_data_path}\diary\2026-07-17.md"
   Copy-Item -Path $src -Destination $dst -Force
   ```

4. 重启 LifePrism 服务
5. 恢复 `sync_client`（下次同步会触发 CONFLICT，预期行为）

### Q2：如何恢复某天的数据库状态？

**场景**：数据库被破坏，希望恢复到 2026-07-17 16:00 的状态。

**步骤**：

1. **关闭 LifePrism 服务**（必须停服，详见第 5 章）
2. 预恢复备份当前数据库（复制到 `backups/pre_restore-{ts}.db`）
3. 选择备份：`{lifeprism_data_path}/backups/db/lifewatch_ai-2026-07-17T16-00-00.db`
4. 替换主数据库：

   ```powershell
   $src = "{lifeprism_data_path}\backups\db\lifewatch_ai-2026-07-17T16-00-00.db"
   $dst = "{lifeprism_data_path}\dataset\lifewatch_ai.db"
   Copy-Item -Path $src -Destination $dst -Force
   ```

5. 重启 LifePrism 服务
6. 验证心情、日记、习惯打卡等数据是否正常

### Q3：如何恢复被误删的 agent 配置？

**场景**：误删了 `agent/behavior.md` 或 `agent/identity.md`，希望恢复。

**步骤**：

1. 暂停 `sync_client`
2. 定位备份中的 agent 配置：

   ```powershell
   # 列出最近的备份时间戳
   Get-ChildItem "{lifeprism_data_path}\backups\docs\" -Directory | Sort-Object Name -Descending | Select-Object -First 3
   ```

3. 从最新备份复制目标文件：

   ```powershell
   $ts = "2026-07-17T03-00-00"  # 替换为实际时间戳
   $src = "{lifeprism_data_path}\backups\docs\$ts\agent\behavior.md"
   $dst = "{lifeprism_data_path}\agent\behavior.md"
   Copy-Item -Path $src -Destination $dst -Force
   ```

4. 重启 LifePrism 服务，恢复 `sync_client`

### Q4：恢复后下次同步会发生什么？

**文档恢复后**：
- `file_sync_state` 中的 `current_hash` 与新文件 hash 不匹配
- 下次同步触发 CONFLICT 状态（**预期行为**）
- 走 diff3 + LLM 辅助合并流程
- 用户需在 Agent 对话中确认合并策略

**数据库恢复后**：
- `file_sync_state` 表整库覆盖，状态以备份为准
- 下次同步以恢复后的状态为基准
- 如与云端有差异，走 diff3 + LLM 辅助合并流程

详见第 7 章。

### Q5：如何从 sync_conflict/ 恢复某个冲突版本？

**场景**：某次同步冲突降级为 `keep_ours`，但事后发现应该用云端版本。

**步骤**：

1. 进入 `sync_conflict/` 目录，按时间戳找到对应的冲突备份：

   ```powershell
   Get-ChildItem "{lifeprism_data_path}\sync_conflict\" -Directory | Sort-Object Name -Descending
   ```

2. 找到目标文件，对比 `.local.md` 和 `.remote.md`：

   ```powershell
   # 对比两个版本
   $ts = "20260717_154500"
   $local = "{lifeprism_data_path}\sync_conflict\$ts\agent__behavior.md.local.md"
   $remote = "{lifeprism_data_path}\sync_conflict\$ts\agent__behavior.md.remote.md"
   # 用 Compare-Object 或文本编辑器对比
   ```

3. 如确认要用云端版本，复制 `.remote.md` 覆盖本地文件：

   ```powershell
   $src = "{lifeprism_data_path}\sync_conflict\$ts\agent__behavior.md.remote.md"
   $dst = "{lifeprism_data_path}\agent\behavior.md"
   Copy-Item -Path $src -Destination $dst -Force
   ```

4. 重启 LifePrism 服务，下次同步会触发 CONFLICT（预期行为）

### Q6：备份文件损坏了怎么办？

**场景**：备份校验失败，或备份文件无法打开。

**识别方法**：
- 查看日志：`{lifeprism_data_path}/debug_logs/lifeprism.log`，搜索 `ERROR` + `备份` 关键词
- 数据库备份损坏：用 DB Browser for SQLite 打开时报错
- 文档备份损坏：文件数量与源不一致，或文件 hash 不匹配

**系统自动处理**：
- 校验失败的备份会被**自动删除**（文档备份目录或数据库备份文件）
- 记录 ERROR 日志，不影响其他任务
- 下次备份时仍会生成新备份

**用户手动处理**：

1. 检查磁盘空间是否充足：

   ```powershell
   Get-PSDrive | Where-Object {$_.Name -eq "C"}
   ```

2. 检查 `{lifeprism_data_path}/backups/` 目录读写权限
3. 如所有备份都损坏（极端情况）：
   - 检查 `sync_conflict/` 是否有冲突备份可用
   - 联系开发者或从外部备份恢复
   - 查看 `docs/history-bugs/2026-07-16-conflict-resolve-llm-destroys-behavior-md.md` 了解类似事件

## 10. 技术附录（面向 Agent 与开发者）

### A.1 备份调度机制

- **调度器**：复用 `ScheduleService`（基于 APScheduler 的 `AsyncIOScheduler`）
- **触发机制**：Cron 表达式
  - 文档：`0 3 * * *`（每天本地 03:00）
  - 数据库：`0 0,8,16 * * *`（每天本地 00/08/16 点）
- **时区**：本地时区（`pytz.timezone(get_user_timezone())`）
- **run_mode 守卫**：`run_mode != "full"` 时跳过备份（云端 `agent_only` 与 `web_demo` 模式不备份）
- **状态持久化**：复用 `_save_cron_state` 机制，避免重启后重复执行
- **启动补偿**：错过 03:00 时启动后异步执行一次

### A.3 SQLite Online Backup API

```python
import sqlite3

source = sqlite3.connect("{lifeprism_data_path}/dataset/lifewatch_ai.db")
target = sqlite3.connect("{lifeprism_data_path}/backups/db/lifewatch_ai-{timestamp}.db")
source.backup(target)  # 在线拷贝，不阻塞业务读写
target.close()
source.close()
```

**为什么使用 SQLite Online Backup API**：

1. **在线拷贝**：不阻塞业务读写（生产环境可继续写入）
2. **原子性**：备份过程原子，不会产生半截损坏文件
3. **路径自定义**：完全自定义目标路径，避免文件锁冲突
4. **可读性**：产物是普通 `.db` 文件，可用 DB Browser 直接打开
5. **比文件复制更可靠**：避免 SQLite WAL 模式下文件复制可能丢失数据的问题

### A.4 PRAGMA integrity_check

```python
import sqlite3

conn = sqlite3.connect("{backup_path}")
cursor = conn.cursor()
cursor.execute("PRAGMA integrity_check")
result = cursor.fetchone()[0]
conn.close()

# result == "ok" → 校验通过
# result != "ok" → 校验失败，删除损坏备份
```

**作用**：

- 检查 SQLite 数据库的完整性（B-tree 结构、索引、外键等）
- 是 SQLite 内置的官方校验机制
- 比文件大小或 hash 校验更可靠（hash 只能检测字节级损坏，无法检测逻辑损坏）

### A.5 平铺存储设计理由

文档备份采用**平铺存储**（非 zip 压缩）：

1. **用户可直接用文件管理器查看备份内容**（关键需求，ADR 决策依据）
2. **单文件恢复只需复制**，无需解压
3. **数据库 `.db` 文件可用 DB Browser 直接打开**
4. LifePrism 数据量小（文档几 MB、数据库几 MB），3 份总和不超 50MB，无压缩需求
5. 现代备份工具（restic、borg）均采用平铺 + 去重，zip 适合归档不适合备份

### A.6 备份完整性校验

**文档备份校验**：
1. 文件数量比对：源文件数 == 备份文件数
2. 文件列表比对：相对路径集合一致
3. 文件内容比对：每个文件 SHA-256 hash 一致

**数据库备份校验**：
- `PRAGMA integrity_check` 返回 `ok`

**校验失败处理**：
- 删除损坏的备份目录/文件
- 记录 ERROR 日志（含失败原因）
- 不影响其他任务（调度器独立）

### A.7 保留策略

- **文档备份**：保留最新 3 份（按时间戳字符串降序排序，删除超出的旧备份）
- **数据库备份**：保留最新 3 份（同上）
- **sync_conflict/ 备份**：保留 30 天（按时间戳目录名排序，删除超期目录）
- **pre_restore-* 快照**：不自动清理（用户手工管理）
