### 阶段 4：架构重新讨论——真正困难的部分（过程.md Prompt 27-87）

这是整个过程中最长、最消耗精力的阶段。核心困难不在于"要不要用 ISO"，而在于以下几个**具体的架构难题**：

#### 困难 A：硬编码本地时间如何处理？

**Prompt 39 和 Prompt 41 专门讨论这个问题**：

代码中存在大量硬编码的本地时间逻辑：
- `DAILY_START_HOUR = "04:00:00"`（每天开始时间是凌晨4点，本地概念）
- `f"{date} 04:00:00"` 构造查询时间范围
- `_dreaming()` 中的"昨天"计算（本地时间的昨天）
- report service 中按本地日期分组统计

**核心矛盾**：这些时间用本地时区思考非常直观（"凌晨4点"就是凌晨4点），但内部存储是 UTC，"本地凌晨4点"在 UTC 是"前一天20点"，逻辑非常反直觉。如果全部改用 UTC 思考，代码可读性大幅下降；如果保留本地时间构造，则需要在使用时就地转换。

**用户的决策**（Prompt 73）：硬编码本地时间是正确的（逻辑直观），但必须在**使用时马上就地转换成 UTC ISO**，不能让本地时间字符串流入查询层。

#### 困难 B：转换在哪里发生？execute 层还是工具函数内部？

这是**花费时间最多的争议点**。

用户的意图很明确（Prompt 37、63、73）：
> "在 tool 的 execute 中进行时间转换"——即 LLM 工具的入口（execute 方法）负责把 LLM 传入的本地时间转为 UTC，工具函数内部只处理 UTC 时间，输出时也在 execute 层或显式调用转换函数。

但 AI 的实际做法出现了偏差：
- AI 直接在底层工具函数（如 `query_user_activity_summary`）内部做 `_utc_to_local()` 转换
- 这样做"看起来"工作正常——LLM 调用时能得到本地时间
- 但这是**取巧**，带来两个问题：
  1. **非 LLM 调用方受影响**：dreaming 函数（定时任务）直接 import 并调用 `query_user_activity_summary`，如果函数内部做了 UTC→本地转换，dreaming 拿到的也是本地时间字符串，而 dreaming 可能需要 UTC 时间用于其他计算
  2. **职责不清**：工具函数到底应该返回 UTC 还是本地时间？如果在内部转换，函数签名和文档说接收 UTC 参数，但返回值却偷偷转成本地，违反了"接收什么格式就返回什么格式"的直觉

**Prompt 75 中用户的质疑直接点出了这个问题**：
> "你确定它后面所有的工具都是大模型在它的工序里面引用来的吗？如果说它后面增加一个工具，但是它不是那个大模型的工具呢？因为当前只是为了代码复用性才复用的这个东西……如果你这样做的话，如果后面增加一个工具，它不是大模型直接调用的，因为当前大模型调用它是针对了这个格式和 UTC 的转换。但如果新增加一个，它没有这个东西呢？"

#### 困难 C：dreaming 代码复用导致的职责混淆

代码结构本身存在职责不清的问题：
- `lifeprism/llm/agent/tools/lifeprismsystem.py` 中的 `query_user_activity_summary` 是一个普通 Python 函数
- 它被 `UserActivitySummaryTool.execute()` 包装成 LLM 工具
- 但 `lifeprism/llm/function/agent_schedule_job.py` 的 `dreaming()` 直接 import 并调用这个函数（第17行）
- 也就是说：同一个函数，既是 LLM 工具的底层实现，又是定时任务的直接依赖

AI 在修改时，看到 dreaming 调用了这个函数，就误以为 dreaming 也是 LLM 工具链的一部分，想把转换逻辑放在函数内部"一劳永逸"。但用户的意思是：dreaming 是独立的调用方，它自己负责自己的时间转换（在调用工具函数前把本地时间转成 UTC ISO），工具函数不应该替调用方做转换。

最终的解决方案是：
- 工具函数（如 `query_user_activity_summary`）接收 UTC ISO 参数
- 工具函数内部，**显示用的时间字段**（返回给 LLM 看的时间段标签）调用 `_utc_to_local()` 转换
- **计算用的时间字段**（如 `_category_stats` 中的时间范围比较）保持 UTC ISO
- LLM Tool 的 `execute()` 方法负责把 LLM 传入的本地时间转成 UTC ISO 再调用工具函数
- dreaming 函数自己在调用前用 `local_to_utc_iso()` 转换

这个方案虽然可行，但"工具函数内部对部分字段做显示转换"仍然是一个混合方案，不是完全干净的分层。

#### 困难 D：repo 层返回时间给 LLM 要不要转换？

Prompt 75 用户指出：
> "当前存在逻辑混乱：部分数据经过整合，但有些查询工具直接返回数据库原始时间。这个地方很混乱"

Repository 层查询返回的数据中包含 UTC ISO 时间戳。这些数据流向 LLM 时，是否需要转换？
- 如果在 repo 层转换，所有调用方（包括非 LLM 调用方）都会拿到本地时间，违反"内部用 UTC"原则
- 如果在 tool 层转换，每个工具都要遍历结果做转换，容易遗漏（ListCustomRecordTypesTool 就是这样遗漏的）
- 如果在 execute 层统一转换，需要识别返回结果中哪些字段是时间字段（这就是装饰器方案想解决的问题）

装饰器方案最终被否决，但这个"在哪里转换输出"的问题始终没有完美答案，最终采取的是"工具函数内部显式对显示字段调用转换"的方案。

#### 困难 E：短暂的动摇——不是因为不喜欢 ISO，而是因为太麻烦

Prompt 75 中用户说：
> "动摇了我到底要不要做这个时间转换功能的决策"

这个动摇的原因是：
- 修改内容太多，到处都是时间相关的代码
- 本地时区格式其实"能用"，不是致命问题
- AI 给出的方案不够细致，在重要点上说不清楚（Prompt 43："你给的方案不够细致"）
- 代码职责不清（dreaming 复用问题）导致方案难以干净落地

**不是因为不喜欢 ISO 格式**——对 ISO 格式的偏好讨论发生在 Prompt 27-33 的更早阶段，是关于对外接口格式的讨论，很快就确定了"对外用 YYYY-MM-DD HH:MM:SS 本地格式，对内用 ISO UTC"。Prompt 75 的动摇是对"整个重构是否值得做"的怀疑，被 AI 端逻辑混乱触发的。

#### 困难 F：字符串时间无法判断时区

Prompt 43-57 中 AI 总结的核心难点：
```
"2026-07-12 04:00:00" 既可能是本地凌晨4点，也可能是UTC凌晨4点。一旦混用，无法区分。
```

这直接推动了"所有内部时间统一使用 ISO 带时区标识"的决策落地。

## 二、格式决策的演变（准确版本）

### 阶段 A：ADR 阶段（过程0.md Prompt 2）

**决策**：内部存储 UTC + ISO 8601。清晰正确。

### 阶段 B：对外接口格式讨论（过程.md Prompt 27-33，早期）

讨论焦点：**对外接口**（面向用户和 AI）用什么格式？
- 内部存储：确定是 UTC ISO
- 对外显示：用户觉得 `YYYY-MM-DD HH:MM:SS` 更可读，想保留这个格式
- 这个讨论不是"动摇要不要用 ISO"，而是"对外用什么格式"

最终决定：对外用本地时区 `YYYY-MM-DD HH:MM:SS`，对内用 UTC ISO。这是内外分离原则的一部分。

### 阶段 C：方案信心动摇（过程.md Prompt 75，中期）

触发原因：AI 在转换位置问题上方案不清晰，dreaming 复用问题导致逻辑混乱，让用户觉得"这个重构是否值得做"。这个动摇是对实施方案的怀疑，不是对技术方向的怀疑。很快被"字符串时间无法判断时区"的技术现实拉回来。

### 阶段 D：最终决策

- **内部存储**：UTC + ISO 8601（带 `+00:00`）
- **对外接口（用户/AI）**：本地时区 + `YYYY-MM-DD HH:MM:SS`
- **日期字段**：本地日期 `YYYY-MM-DD`
- **硬编码本地时间**：允许，但必须在使用时马上就地转 UTC ISO
- **转换位置**：execute 层负责输入转换；工具函数内部显式对显示字段调用 `utc_to_local_display()`，计算字段保持 UTC
- **非 LLM 调用方**：自己负责转换，工具函数不替调用方做转换

## 三、问题 1：如何编写 prompt 让 AI 进行全面考察

从本次重构来看，AI 遗漏和误解的因素包括：

| 问题 | 类型 | 为什么发生 |
|------|------|-----------|
| AI/LLM 工具的时间输入输出格式 | 遗漏 | PRD/issue 没提及，AI 没主动识别 LLM 是时间消费方 |
| 用户时区配置 | 遗漏 | PRD 列为 Out of Scope |
| 硬编码本地时间的处理策略 | 遗漏 | 没有区分"硬编码本地时间常量"和"动态生成时间" |
| 代码复用导致的职责混淆 | 误解 | AI 没分析函数调用关系，dreaming 直接调用工具函数被误认为 LLM 链路的一部分 |
| 转换位置的精确语义 | 误解 | 用户说"在 tool 中转换"，AI 理解为"在工具函数内部转换"而非"在 Tool.execute() 层转换" |
| 显示字段 vs 计算字段的区分 | 遗漏 | 没有分析每个时间字段的用途（给人看 vs 用于计算） |
| repo 层返回时间的转换职责 | 遗漏 | 没有分析数据流从 repo 到 LLM 的完整链路 |
| SQLite datetime('now') 的实际输出 | 遗漏 | 假设了数据库会处理格式，没有写最小测试验证 |

### 根本原因

AI 只看到了**机械替换**维度（`datetime.now()` → `datetime.now(timezone.utc)`），没有看到**架构设计**维度：
1. 没有画出函数调用关系图（谁调用谁，哪些是 LLM 入口，哪些是内部函数）
2. 没有区分"时间从哪里来"（生产者）和"时间到哪里去"（消费者）
3. 没有区分每个时间字段的用途（显示 vs 计算）
4. 没有识别"硬编码本地时间"是一个独立的问题类别

### 改进方案：全面考察的 prompt 模板

```
任务：[重构目标]

在编写任何实现方案之前，必须完成以下分析：

1. 列出所有涉及的「时间类型」
   - 动态生成的时间戳（created_at/updated_at）
   - 硬编码的时间常量（如"凌晨4点"、"每天10点"）
   - 日期字段（仅日期，无时间）
   - 相对时间（"昨天"、"今天"、"最近7天"）
   - 时间范围（start_time/end_time）

2. 画出「函数调用关系图」
   - 哪些函数是外部入口（API endpoint、Tool.execute、定时任务入口）？
   - 哪些是内部复用函数（被多个入口调用）？
   - 每个函数接收什么时间格式？返回什么时间格式？
   - 特别标注：是否存在"内部函数被非预期调用方复用"的情况？

3. 画出「数据流图」，标注每个数据类型的：
   - 生产者：谁创建这个数据？（数据库 DEFAULT、代码生成、用户输入、AI 输入、硬编码常量）
   - 消费者：谁读取这个数据？（数据库查询、前端显示、AI 提示词、日志、内部计算）
   - 存储位置：数据存在哪里？（数据库列、API 响应、配置文件、内存变量）
   - 用途：给人看的（显示）还是机器用的（计算/比较）？

4. 对每个「消费者」，回答：
   - 它需要什么格式？什么时区？
   - 它能否理解时区标识？
   - 它接收到错误格式时会怎样（静默错误 vs 显式报错）？

5. 列出所有「边界场景」：
   - 午夜前后（日期切换）
   - 跨时区（服务器时区 ≠ 用户时区）
   - 混合格式共存（迁移过渡期）
   - 字符串比较 vs datetime 比较
   - 硬编码本地时间转换为 UTC 后的可读性

6. 明确「转换职责边界」：
   - 输入转换在哪里做？（入口层统一做 vs 每个函数自己做）
   - 输出转换在哪里做？（返回前统一做 vs 调用方自己做）
   - 内部复用函数是否应该做转换？（如果做，非预期调用方怎么办？）

7. 只在完成以上分析后，才提出实现方案。方案中必须标注：
   - 每个转换发生在哪个函数的哪一行
   - 哪些函数是"边界层"（负责格式转换），哪些是"内部层"（只处理一种格式）
```

**为什么这个模板能避免本次的问题**：

- 步骤 1 强制识别"硬编码时间常量"类别——避免硬编码时间处理被遗漏
- 步骤 2 强制画调用关系图——AI 会发现 dreaming 不是 LLM 入口，而是独立的定时任务，不能假设所有调用 `query_user_activity_summary` 的地方都是 LLM 工具链
- 步骤 3 "用途"标注强制区分显示字段 vs 计算字段——避免在计算字段上错误转换
- 步骤 6 强制明确转换职责边界——直接回答"在 execute 层还是工具函数内部"的问题，避免取巧式的在函数内部转换

## 四、用户的决策中值得肯定的地方

在列出错误之前，先肯定几个关键的正确决策：

1. **内外分离原则（就地转换）**（Prompt 37）：这个原则避免了在 API 层或中间件层做统一转换导致的"双时区数据"问题，是正确的架构方向。

2. **硬编码本地时间允许存在，但使用时马上转换**（Prompt 73）：这个决策平衡了代码可读性和格式一致性——不强制所有代码用 UTC 思考（那样太反直觉），但要求本地时间不流入数据层。

3. **要求真实调用而非仅代码分析**（Prompt 91）：这个要求直接发现了 ListCustomRecordTypesTool 的遗漏，是验证环节最关键的决策。

4. **新旧数据库对比验证**（Prompt 109）：828,082 条数据对比是验证迁移完整性的最终手段。

5. **要求端到端 API 测试**（Prompt 19-23）：通过 FastAPI docs 创建数据验证写入格式，发现了 _generic_insert 的问题。

## 五、可以改进的地方及建议

### 问题 1：调研报告产出后，没有将建议转化为可执行的验收标准就分发任务

**表现**：Issue #1 产出了 889 行的隐性依赖报告，明确指出"LLM 上下文时间建议使用本地时间"、"_dreaming() 的昨天是本地语义"等关键建议，但后续所有 issue 只是加了一行"参考 utc-migration-hidden-dependencies.md"，验收标准仍是机械替换（`datetime.now()` → `datetime.now(timezone.utc)`），与报告建议直接矛盾。用户分发完 issue 后直接去睡觉了，没有亲自审阅报告。

**后果**：
- 子 agent 按验收标准执行，把 context.py 的时间改成了 UTC，与报告建议相反
- 报告中的错误结论（3 张旧表不需要迁移）被 m009 直接照搬
- 报告中标记为"低风险"的 LLM 时间问题，实际上是高风险的架构问题

**改进**：调研报告产出后，**必须有一个人工审阅步骤**，做三件事：
1. 确认报告中的结论是否正确（特别是"XX 已经是 UTC"这类断言）
2. 将报告中的"建议"逐条转化为具体 issue 的验收标准（而不是只加一行"参考文档"）
3. 如果报告发现的问题与 PRD/issue 的默认假设矛盾，必须先解决矛盾再分发任务

不能让子 agent 自己判断如何"参考"一份 889 行的文档——子 agent 倾向于按照最直接的验收标准（机械替换）执行，忽略文档中标记为"低风险"但实际上是架构性建议的内容。

### 问题 2：PRD 缺少"调用关系"和"格式契约"分析

**表现**：PRD 只分析了"哪些文件有 datetime.now()"，没有分析"哪些函数是边界层、哪些是内部层、每个函数的输入输出格式契约是什么"。

**后果**：AI 实现时无法判断转换应该放在哪里，导致在工具函数内部取巧式转换，dreaming 复用问题暴露后才发现职责不清。

**改进**：在 PRD 之前增加一个步骤——**接口格式契约分析**。对所有涉及时间的函数，标注"接收什么格式、返回什么格式、是否是边界层函数"。边界层函数（API endpoint、Tool.execute、定时任务入口）负责转换，内部函数只处理一种格式。

### 问题 3：Issue 切分没有包含"架构规则验证"类 issue

**表现**：19 个 issue 全是"修改 XX 模块"类，没有一个 issue 是"验证所有转换都发生在正确位置"。

**后果**：ListCustomRecordTypesTool 在 `99ed794` 中仍然遗漏，因为没有 issue 专门检查"所有 LLM Tool 的 execute 方法是否正确转换了输入、所有输出的显示字段是否正确转换"。

**改进**：切分 issue 时，除了"修改"类 issue，增加"规则验证"类 issue——专门验证架构规则被遵守（如"所有 LLM 工具输出不含 UTC ISO 时间戳"）。

### 问题 4：对 AI 的指令不够精确

**表现**：用户说"在 tool 中转换"，AI 理解为工具函数内部，但用户实际意思是 Tool 类的 execute 方法。

**原因**："tool"这个词在代码中有两层含义——底层工具函数（query_user_activity_summary）和 Tool 类包装器（UserActivitySummaryTool）。用户说的是后者，AI 理解成了前者。

**改进**：给 AI 精确到代码结构的指令，例如："在继承自 Tool 的类的 execute() 方法中进行输入转换（本地时间→UTC ISO），工具函数本身不做输入转换"。最好直接给出代码示例说明期望的模式。

### 问题 5：迁移脚本基于 schema 假设而非代码审计

**表现**：m009 脚本注释"todo_list.created_at 已排除（CURRENT_TIMESTAMP = UTC）"，但实际历史数据是代码显式写入的本地时间。隐性依赖报告的错误结论（§4.3 第706行）被直接照搬。

**改进**：迁移脚本的字段审计应基于：
1. `grep -n "INSERT INTO" -r lifeprism/` 找出所有显式写入时间字段的代码
2. `grep -n "UPDATE.*SET" -r lifeprism/` 找出所有显式更新时间字段的代码
3. 确认每个时间字段的实际写入来源，而非看 schema DEFAULT
4. 对调研报告中"XX 已经是 UTC"这类断言，必须用实际数据验证（SELECT 一条记录看格式）

### 问题 6：数据流分析在验证阶段才做，而不是在设计阶段

**表现**：Prompt 19 才派 subagent 做"哪些表由什么渠道产生"的数据流分析。

**改进**：数据流分析（谁生产、谁消费、格式是什么）应该是架构分析阶段的产出，作为 issue 切分的输入，而不是实现后的验证手段。

### 问题 7：没有在阶段 0 写最小验证测试

**表现**：SQLite `datetime('now')` 的输出格式是在 API 测试时才发现的。

**改进**：架构决策后、实现前，写几个最小测试验证关键假设：
- SQLite `datetime('now')` 实际输出什么格式？
- `datetime('now', 'localtime')` 实际输出什么格式？
- 带时区的 ISO 字符串和不带时区的字符串在 SQLite 中比较是否正确？
- 报告说"XX 表已经是 UTC"——SELECT 一条记录验证

每个测试 30 秒能跑完，但能避免后续大量返工。

```
Step 0: ADR 决策（L1：时区 + 内部存储格式）

  └─ 验证：为每个候选格式列出"出错场景"

Step 1: 隐性依赖调研（先调研再切 issue）
  ├─ 产出：隐性依赖排查报告（代码搜索 + 业务逻辑审查）
  └─ ⚠️ 人工审阅点：确认报告结论正确，特别是"XX已经是UTC"类断言

Step 1.5: 架构分析（最关键的步骤）
  ├─ 产出1：函数调用关系图（区分入口层 vs 内部复用层）
  ├─ 产出2：数据流图（生产者/消费者/用途：显示vs计算）
  ├─ 产出3：接口格式契约（每个边界函数接收/返回什么格式）

  ├─ 产出5：边界场景清单

Step 2: PRD 编写
  ├─ 输入：Step 0 + Step 1 + Step 1.5

Step 3: Issue 切分
  ├─ 将调研报告的每条建议转化为具体的验收标准（不是只加一行"参考文档"）

  ├─ 前置：grep所有INSERT/UPDATE审计时间字段写入来源
  ├─ 前置：SELECT实际数据验证"XX已经是UTC"类断言
  ├─ 迁移脚本基于代码审计，非schema假设
  └─ 动态发现表（SELECT FROM sqlite_master）

Step 6: 端到端验证
  ├─ API测试（FastAPI docs逐个调用，检查DB中格式）
  ├─ LLM工具真实调用（检查输出不含+00:00）
  ├─ 架构规则验证（检查没有内部函数偷偷做转换）
```

## 七、总结

### 本次重构真正的困难排序

1. **转换位置的职责边界**（最耗时）：execute 层 vs 工具函数内部 vs repo 层，叠加代码复用（dreaming 直接调用工具函数）导致职责混淆，这是花费 prompt 最多的问题。
2. **硬编码本地时间的处理策略**：本地时间思考直观但 UTC 存储，矛盾如何调和。
3. **显示字段 vs 计算字段的区分**：同一个返回结果中，有些字段需要转本地（给人看），有些要保持 UTC（用于计算），无法用统一装饰器处理。
4. **字符串时间无法判断时区**：直接推动了 ISO 带时区标识的决策落地。
5. **首批实现返工**：架构未定稿就实现，导致 19 个 issue 中大量内容需要重做。

### 成本构成（修正版）

| 成本类型 | 估计占比 | 说明 |
|---------|---------|------|
| 转换位置职责讨论（困难B+C+D） | ~30% | execute层vs函数内部、dreaming复用、repo输出转换 |
| 硬编码时间处理策略讨论（困难A） | ~15% | 凌晨4点、DAILY_START_HOUR等 |
| 首批实现返工 | ~20% | 架构未定稿就开始实现 |
| 迁移脚本补救 | ~15% | m009漏迁+动态表 |
| 验证发现问题修复 | ~10% | ListCustomRecordTypesTool等 |
| 有效工作 | ~10% | 基础设施+最终正确的实现 |

### 一句话原则

> **调研先于切分，审阅先于分发：调研报告产出后必须人工审阅确认结论、将建议转化为验收标准后才能分发任务；架构分析先于实现，画调用关系图区分入口层与内部层；最小测试验证关键假设，真实调用验证最终结果。**

## 八、元问题：如何与 AI 协作完成复杂任务

> UTC 时区迁移暴露的不是时区问题，而是**人类与 AI 协作处理复杂任务时的系统性失败模式**。本节不给出具体方案，而是先把问题本身梳理清楚——问题地图是什么，有哪些阶段，每个阶段的核心挑战是什么。

### 8.1 问题的本质

复杂任务（如跨模块重构、架构迁移）有一个根本特征：**开始时你不知道自己不知道什么**。UTC 迁移中，以下问题在开始时都没有被识别：

- AI 端（LLM）需要本地时间而非 UTC——这是"未知的未知"
- 硬编码本地时间（凌晨4点）需要独立处理策略——这是"已知的未知"但被低估
- dreaming 复用 LLM 工具函数导致职责混淆——这是代码层面的隐性依赖
- 调研报告中"3张旧表已经是UTC"是错误结论——这是调研本身的可靠性问题

问题不是"AI不够聪明"或"用户不够仔细"，而是**没有一套系统化的流程来管理未知、管理注意力、管理决策节奏**。

### 8.2 问题地图：三类核心问题

#### A. 宏观问题（任务启动与架构阶段）

| # | 问题 | UTC迁移中的表现 |
|---|------|----------------|
| A1 | **决策过快**：任务刚开始时，在信息不足的情况下快速做出决策并推进 | ADR后直接切19个issue，没有L2架构分析 |
| A2 | **PRD不足以承载规则**：光有产品需求文档不够，还需要规则文档/架构约定文档 | PRD写了Implementation Decisions，但缺少"每层格式契约"和"转换职责边界" |
| A3 | **未知的未知无法主动发现**：如何确定"自己不知道什么"？ | LLM需要本地时间、dreaming复用问题、硬编码时间——都是事后才发现 |
| A4 | **调研报告的结论没有被验证**：调研产出了报告，但报告本身可能有错误 | 报告说"3张旧表已经是UTC"，这是错误的，但没有验证就被m009照搬 |
| A5 | **阶段回退边界模糊**：架构→执行→验证中发现新问题，何时应该退回架构阶段？ | LLM工具时间格式问题在实现后才发现，退回架构讨论花了60条prompt |
| A6 | **过程无章法无记录**：哪些问题已经决策、哪些悬而未决、哪些被忽略——没有记录 | 讨论中多次出现"这个之前说过吗"的回溯 |

#### B. 微观问题（对话与执行阶段）

| # | 问题 | UTC迁移中的表现 |
|---|------|----------------|
| B1 | **人类是决策瓶颈**：一瞬间涌上来的信息量太大，人不可能马上做出很多决策 | 用户说"方案不够细致，重要点没说清楚"，因为AI一次抛出太多问题 |
| B2 | **选择性关注（确定性偏好）**：AI倾向于回答确定的问题，对模糊的问题不感兴趣；用户也只对感兴趣的问题作答 | 用户模糊地提出"AI端时间格式"问题，AI在首次实现中忽略了 |
| B3 | **分支丢失**：一次讨论有多个分支问题，一次只能处理一个，处理完后注意力被稀释，之前的分支被遗忘 | 讨论转换位置时，同时存在execute层vs函数内部、硬编码时间、repo输出转换三个分支，硬编码时间的讨论被推后了 |
| B4 | **静默忽略**：被忽略的问题可能很重要，但没有记录，被静默丢弃 | 隐性依赖报告提到"LLM上下文时间建议用本地时间"，但被标记为"低风险"，后续issue完全没处理 |
| B5 | **留痕不清**：AI给出的内容重点不明确、优先级不明确、不决策的后果不明确 | AI给出方案时没有标注"这个点必须你确认，否则会导致XX问题" |
| B6 | **确认时机不明**：哪些问题必须在哪个阶段确认？哪些可以延后？ | "用户时区配置"被列为Out of Scope，但后来发现是核心需求 |
| B7 | **意图误解**：用户说"在tool中转换"，AI理解为工具函数内部而非Tool.execute() | 词汇歧义（tool有两层含义）没有被主动澄清 |

#### C. 流程交接问题（阶段转换与Agent分发）

| # | 问题 | UTC迁移中的表现 |
|---|------|----------------|
| C1 | **"参考文档"等于"不参考"**：后续issue只写"参考XX文档"，但子agent不会真正消化文档 | 18个issue都写了"参考utc-migration-hidden-dependencies.md"，但关键建议被忽略 |
| C2 | **矛盾没有被识别**：调研报告建议与验收标准直接矛盾，但没有在分发前发现 | 报告说LLM时间用本地，issue验收标准说全部改成UTC |
| C3 | **分发前没有审阅**：用户分发完issue直接去睡觉，没有亲自审阅调研报告 | 报告错误结论和矛盾都没被发现 |
| C4 | **子agent的注意力范围有限**：子agent按验收标准执行，不会主动识别标准之外的问题 | Issue #10按标准把context.py改成了UTC，虽然报告建议用本地时间 |

### 8.3 阶段定义与每个阶段的核心挑战

基于UTC迁移经验，复杂任务可分为以下阶段。注意：阶段之间不是严格线性的，允许回退。

```
┌─────────────────────────────────────────────────────────┐
│  Phase 0: 触发与感知                                      │
│  "我意识到需要做一个复杂任务"                               │
│  核心挑战：正确理解任务边界，不急于动手                        │
├─────────────────────────────────────────────────────────┤
│  Phase 1: 探索与调研                                      │
│  "我需要先了解现状"                                        │
│  核心挑战：让未知显形，不做假设，验证调研结论                  │
├─────────────────────────────────────────────────────────┤
│  Phase 2: 架构与决策                                      │
│  "我需要决定怎么做"                                        │
│  核心挑战：决策节奏管理——不做过快决策，也不陷入分析瘫痪          │
├─────────────────────────────────────────────────────────┤
│  Phase 3: 规则与契约                                      │
│  "我需要把决策转化为可执行的规则"                             │
│  核心挑战：规则足够具体到AI不会误解，但不腐烂                  │
├─────────────────────────────────────────────────────────┤
│  Phase 4: 切分与分发                                      │
│  "我需要把任务拆成AI可执行的单元"                             │
│  核心挑战：验收标准与规则一致，建议转化为可检查项               │
├─────────────────────────────────────────────────────────┤
│  Phase 5: 执行与监控                                      │
│  "AI在干活，我需要监控"                                    │
│  核心挑战：及时发现问题，决定是否回退                          │
├─────────────────────────────────────────────────────────┤
│  Phase 6: 验证与收尾                                      │
│  "做完了，需要确认正确"                                    │
│  核心挑战：验证覆盖了消费者，而不仅是生产者                     │
└─────────────────────────────────────────────────────────┘
```

#### Phase 0：触发与感知

**特征**：用户意识到需要做某件复杂的事（如"时区不一致导致数据同步问题"）。

**UTC迁移中的状态**：用户通过数据同步的LWW问题意识到时区问题，快速做了ADR决策。

**核心失败模式**：
- 触发问题被当作全部问题（时区→UTC只是LWW的解，但不是全部问题）
- 太快进入"怎么做"，没有充分理解"问题有多大"

**本阶段必须回答的问题**：
- [ ] 这个问题的边界是什么？（哪些模块/层受影响？）
- [ ] 我现在知道什么？不知道什么？
- [ ] 这是一个"机械替换"还是"架构重设计"？如何判断？

#### Phase 1：探索与调研

**特征**：派出AI做调研，了解代码现状和隐性依赖。

**UTC迁移中的状态**：Issue #1产出了889行的隐性依赖报告，质量相当高。

**核心失败模式**：
- 调研报告可能有错误结论（"3张旧表已经是UTC"）
- 调研报告标记的"风险等级"可能不准确（LLM时间标记为"低风险"实际是高风险）
- 调研只做代码搜索，不做调用关系分析（函数之间谁调用谁）

**本阶段必须回答的问题**：
- [ ] 所有涉及的数据流（生产者→消费者→存储）是否已画出？
- [ ] 调研报告中的关键断言（"XX已经是UTC"）是否已用实际数据验证？
- [ ] 是否存在"代码复用但职责不同"的情况（如dreaming调用LLM工具函数）？
- [ ] 调研中发现的问题是否按"不修改会怎样"分级，而不是按"看起来像什么"分级？

#### Phase 2：架构与决策

**特征**：基于调研结果做架构决策。这是最消耗认知资源的阶段。

**UTC迁移中的状态**：这个阶段花了~60条prompt（约40%的成本），但大部分是在实现后才做的。

**核心失败模式**：
- **决策过快**：信息不足时就决策，后来返工
- **决策过慢**：在细节上纠结，不区分"必须现在决策"和"可以延后决策"
- **决策无记录**：决策了但没写下来，后面反复讨论同一个问题
- **分支丢失**：同时讨论多个问题，一些被遗忘

**本阶段必须回答的问题**：
- [ ] 哪些决策是阻塞性的（不做就无法开始）？哪些是非阻塞的？
- [ ] 是否有决策与调研报告建议矛盾？矛盾是否已解决？
- [ ] 每个决策是否记录了"为什么选A不选B"？
- [ ] 悬而未决的问题是否有记录和追踪机制？
- [ ] 决策节奏是否合理？（不是一次做所有决策，而是按依赖顺序）

#### Phase 3：规则与契约

**特征**：把架构决策转化为具体的规则和接口契约。PRD不足以承载这个——需要规则文档。

**UTC迁移中的状态**：time-handling-rules.md经历了v1→v2→v3三次重写，直到v3才是"规则导向"而非"说明导向"。

**核心失败模式**：
- 规则太具体（写死函数名和文件路径），导致文档腐烂
- 规则太模糊（"注意时区转换"），AI无法执行
- 规则只说"做什么"不说"不做什么"（AI不知道什么是错的）
- 没有接口格式契约（每个函数接收什么格式、返回什么格式）

**本阶段必须回答的问题**：
- [ ] 规则是否足够具体到AI不会误解，但足够抽象到代码重构后仍然有效？
- [ ] 边界层函数的输入输出格式契约是否明确定义？
- [ ] 规则中是否包含反例（"不要这样做"）？
- [ ] 规则是否区分了"显示字段"和"计算字段"等不同用途？

#### Phase 4：切分与分发

**特征**：把任务拆成issue/子任务，派发给AI执行。

**UTC迁移中的状态**：19个issue按模块切分，每个都加了"参考文档"一行，但没有将建议转化为验收标准。

**核心失败模式**：
- "参考文档"不等于"消化文档"（C1）
- 验收标准与规则/调研报告矛盾（C2）
- 切分维度错误（按模块而非按数据流路径）
- 没有"规则验证"类issue，只有"修改"类issue

**本阶段必须回答的问题**：
- [ ] 每条规则是否对应至少一个验收标准（可以被检查的）？
- [ ] 调研报告的每条关键建议是否转化为了验收标准？
- [ ] 验收标准中是否有与规则矛盾的内容？
- [ ] 是否有专门的issue验证"规则被遵守"，而不仅是"代码被修改"？
- [ ] 切分维度是否正确（按数据流路径/边界层而非按代码模块）？

#### Phase 5：执行与监控

**特征**：AI在执行任务，用户需要监控进展和质量。

**UTC迁移中的状态**：首批19个issue一次性派发，用户去睡觉，没有中间监控。回来后发现大量问题。

**核心失败模式**：
- 一次性派发太多任务，问题批量出现
- 没有在关键节点停下来验证（如基础设施完成后验证，再继续上层）
- 发现问题后不确定是应该局部修复还是退回架构阶段

**本阶段必须回答的问题**：
- [ ] 第一批任务是否应该限制范围（如只做基础设施，验证后再做上层）？
- [ ] 发现的问题是"执行错误"（AI没按规则做）还是"规则缺陷"（规则本身有问题）？
- [ ] 如果是规则缺陷，是否需要回退到Phase 2/3？

**回退到架构阶段的信号**：
- 发现新的"消费者"之前没有分析到（如UTC迁移中发现LLM是消费者）
- 发现规则在某个场景下无法应用（如装饰器方案无法处理显示vs计算字段）
- 发现两个规则之间存在矛盾

#### Phase 6：验证与收尾

**特征**：代码改完了，需要验证正确性。

**UTC迁移中的状态**：这个阶段做得相对好——API端到端测试、LLM工具真实调用、新旧数据库对比，发现了ListCustomRecordTypesTool遗漏和m009漏迁。

**核心失败模式**：
- 只验证"生产者写对了"（新创建的数据格式正确），不验证"消费者读懂了"（LLM工具输出正确、前端显示正确）
- 只做代码审查，不做真实调用
- 验证脚本基于与迁移脚本相同的假设（如"3张旧表已经是UTC"），无法发现假设错误

**本阶段必须回答的问题**：
- [ ] 是否验证了所有消费者（不仅是写入路径）？
- [ ] 是否有真实调用（而非仅代码分析/单元测试）？
- [ ] 验证逻辑是否独立于实现逻辑（不是用同一份假设来验证假设）？
- [ ] 新旧数据对比是否覆盖了所有表和字段？

### 8.4 对话中的注意力管理问题（微观问题深化）

UTC迁移中反复出现的一个对话模式：

```
用户提出多个问题/关注点（可能有些模糊，有些明确）
  → AI挑选最明确、最容易回答的问题进行回答
  → 模糊的问题被忽略或一笔带过
  → 讨论聚焦在一个分支上
  → 这个分支解决后，其他分支被遗忘
  → 后来在执行中发现被遗忘的分支是关键问题
  → 回退讨论
```

**具体例子**：Prompt 37用户提出"就地转换"原则时，同时隐含了多个问题：
- AI端用什么时间？（模糊提及，未展开）
- 转换在哪里做？（明确：组件/本地，就地转换）
- 硬编码本地时间怎么办？（完全没提，后来在Prompt 41才单独提出）
- repo层输出给LLM时要不要转换？（Prompt 75才提出）

AI只处理了最明确的"转换在哪里做"，其他问题被静默忽略。

**这个问题的根因是双方的**：
- **用户方**：一次提出多个问题，有些模糊（自己也没想清楚），没有明确优先级
- **AI方**：对模糊问题倾向于跳过或给一个泛泛的回答，不主动追问澄清，不记录未回答的问题
- **系统性**：对话没有"开放问题清单"机制，未回答的问题没有追踪

### 8.5 人是瓶颈——决策节奏问题

复杂任务中，用户（人）是决策瓶颈。一瞬间涌上来的决策点太多，人不可能全部处理。

UTC迁移中，用户在Prompt 43明确表达了这个状态：
> "你给的方案不够细致。在一些重要的点上，你没有说清楚"

AI一次抛出了太多需要决策的点，用户无法在短时间内全部消化。这导致：
1. 用户只关注自己最关心/最确定的点
2. 其他点被默认接受（但AI的默认方案可能是错的）
3. 后来发现默认接受的点有问题，返工

**这不是"用户应该更仔细"的问题，而是流程设计的问题**。流程需要：
- 控制每个决策点的粒度（不要一次抛出10个决策）
- 明确标注每个决策的阻塞性（"这个必须现在决策，否则会影响XX" vs "这个可以延后"）
- 明确标注每个决策不做的后果
- 给决策留出"发酵时间"（用户可以慢慢想，AI记录问题但不催促）
