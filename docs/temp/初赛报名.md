# 1. Demo 简介

**是什么：** 一个记录自己的工具。

我们每天都在经历大量的事情——在电脑前做了什么、完成了哪些目标、产生了什么情绪、养成了什么习惯。但这些稍纵即逝，如果不记录，很快就会遗忘。

LifePrism 做的事情很简单：**帮你把这些记录下来。**

它基于 Electron 桌面应用，通过自动追踪、半自动浮窗、手动输入三种方式，覆盖你在电脑前的行为记录和内心世界的感受记录。记录下来的数据不是沉睡的——AI 会帮你整理、关联、提炼，让你从记录中看清自己。

**面向谁：** 所有想要了解自己的人。学生、职场人、自由职业者，只要你每天在电脑前度过大量时间，想要知道自己做了什么、感受如何、变化在哪里，这个工具就是为你准备的。

## 记录自己的三种方式

LifePrism 提供三种记录模式，从完全自动到完全手动，覆盖不同的记录需求：

- **自动记录 — 电脑使用日志 + 截图 AI 分析**：后台静默运行，不需要任何操作。自动记录你的应用使用、窗口切换，周期截图让 AI 理解你正在做什么。每个行为都会被自动分类（工作/学习/娱乐等），生成时间分布图表和行为摘要。**就像一台自动相机，默默拍下你的一天。**

![lifewatch|690x429](upload://m19SpbLKlGo4qnCIf2ALRWmpAvl.gif)

- **半自动记录 — WAID 浮窗**：一个常驻桌面的轻量浮窗，不打断心流。当你要开始一项任务时，在浮窗里点击开始，它会实时计时；结束后自动将这条记录写入时间线。**适合需要精确记录某段时间在做什么的场景。**

![waid窗口介绍|690x388](upload://iDABDOCOBs19jz49gt40m31YYiL.gif)

- **手动记录 — 自定义你想要的任何记录类型**：这是 LifePrism 最核心的记录能力。它不再是固定的"日记""习惯""心情"等预设模块，而是允许你创建**任何**你想记录的类型。比如"饮食记录""付款记录""锻炼记录""追剧记录""梦境记录""灵感记录"……只要你能描述，AI 就会自动生成对应的记录表单。**不仅如此，你还可以在微信对话中直接告诉 AI 你想记录什么**，它会帮你自动完成——不用打开电脑，掏出手机说一句话就行。

![微信通道|230x500](upload://QeJyJXUeT02dtI17DLmpcYoRuj.jpeg)

## 记录带来什么？——从记录到认识自己

记录本身不是目的，认识自己才是。当数据积累到一定程度，LifePrism 帮助你从记录中发现规律：

- **目标设定与追踪**：将目标拆解为计划书→任务池→日历分配，每条时间记录自动关联到对应目标，让你清楚看到**为目标付出了多少时间**。

![目标界面|690x429](upload://目标界面.gif)

- **习惯打卡**：渐进式等级系统（从萌芽到根深蒂固），12 周热力图追踪习惯养成过程。**记录每一次打卡，见证习惯如何从刻意变成自然。**

- **日记与心情**：Markdown 日记支持模板与 AI 摘要，8 种心情维度记录并标注诱发因素。**你逐渐会看到：什么事情让你开心、什么事情让你焦虑，以及你的情绪是否有周期性规律。**

- **聊天记录**：保存重要的微信对话内容，AI 自动提炼要点和行动项。

- **时间使用记录**：记录某一段时间做了什么具体内容，支持时间块标注和回顾。

# 2. Demo 创作思路

## 灵感来源

这个项目的起点很简单：**我想记录自己，但我做不到。**

作为一名研二学生，我每天在电脑前超过 10 小时。到了晚上想回忆今天做了什么、情绪如何、有什么收获，却常常一片空白。那些时间像是被偷走了。我试过各种记录工具——时间追踪、日记、习惯打卡、心情记录——但它们都有一个共同的问题：**每一种记录都是孤立的，而且记录的负担太重了。**

久而久之我发现，问题不在于"需不需要记录"，而在于两个根本性的矛盾：

1. **记录越详细，成本越高；记录越简单，价值越低。** 完全手动记录（写日记、打卡）需要极大的自律，大多数人坚持不过一周；完全自动记录（时间追踪）虽然零成本，但只能告诉你"用了3小时浏览器"，无法回答"这3小时是在深度阅读还是无意义刷网页"。

2. **数据之间没有连接。** 时间管理、习惯、日记、心情散落在不同工具里，你永远无法回答这样的问题：情绪低落的日子是否与某个习惯中断有关？目标进度缓慢是因为时间分配问题还是计划本身不合理？

真正的转折点是接触了接纳承诺疗法（ACT）。它强调：**改变的第一步不是"我要更努力"，而是"我先看清自己"。** 我想，如果有一个工具能帮我持续记录外在行为和内在感受，并且把两者关联起来——那我是不是就能真正看清自己了？

LifePrism 由此诞生。名字的含义是：像三棱镜分解光谱一样，把生活的复杂性分解为可见、可理解、可行动的维度。

## 想解决的问题

1. **记录成本过高** — 传统记录工具要么全手动（成本高难坚持），要么全自动但停留在表面数据。LifePrism 提供自动/半自动/手动三种模式，并且通过微信对话就能记录，让记录的门槛降到最低。
2. **记录内容碎片化** — 时间、习惯、心情、目标各自独立记录，数据之间无法形成关联洞察。LifePrism 将多源数据汇聚到统一的时间线上，AI 可以交叉分析。
3. **记录了但用不上** — 很多人记录了却从不回顾。LifePrism 的 AI 会自动提炼摘要、发现规律、生成报告，让记录真正变成可用的洞察。
4. **记录数据不安全** — 个人时间和心理数据极其敏感。LifePrism 采用本地 SQLite 数据库 + 开源协议（AGPL v3），数据完全在用户掌控之中。

## 为什么坚持"记录自己"这个方向

### 判断 1：AI 最应该做的事情，是替人承担记录的负担，而不是增加交互的负担

市面上很多 AI 工具要求用户主动对话、输入 Prompt 才能获得价值，本质上是用"手动提问"替换了"手动记录"。LifePrism 的设计理念相反：**让 AI 在后台帮你记录和整理**，用户只需在需要时查看分析结果，或者通过微信简单说一句话就能完成记录。

### 判断 2：记录的价值不在量，而在连接

不追求"记录一切"，而是聚焦两个核心维度：**外在行为记录**（你在电脑前做了什么）+ **内在感受记录**（你有什么情绪、想法、目标、习惯）。这两者的交叉分析能回答最有价值的问题——行为与感受如何互相影响，你是一个什么样的人。

### 取舍 1：先做好"记录"，再做"建议"

初期版本专注于帮用户建立记录的习惯和完整的自我画像——通过自动追踪、半自动浮窗、手动输入和微信对话，让记录覆盖尽可能多的场景。AI 的角色是"记录助手"和"洞察提炼者"，而非替你做决策的导师。未来可以基于积累的数据提供更主动的行为干预，但前提是记录本身已经足够完整。

### 取舍 2：专注桌面场景 + 微信补充

深度工作、学习、创作主要发生在桌面环境，所以 LifePrism 是桌面应用。但记录不应该被场景限制——通过微信 Agent 助手，用户可以随时随地说一句话就完成记录，无需打开电脑。

## 我是怎么用 TRAE 把 Demo 做出来的

这个项目从零到 Demo 上线，几乎全部代码由 AI 生成。我把整个过程提炼为**三步工作流**——调研、规则、执行——每一步都依靠 TRAE 的不同能力来支撑。

### 第一步：调研——让 TRAE 把隐性依赖翻出来

复杂任务最怕的不是代码写不出来，而是东西改了之后才发现某个你没想到的模块坏了——「你不知道自己不知道什么」。

我处理这类问题的方式是：**在改任何代码之前，派一个专门的 agent 做全量排查**。TRAE 的智能体支持独立的上下文和工具集，我可以给这个 agent 单独写任务描述，让它搜索所有相关代码、审查业务逻辑、画出调用关系图。它产出的不是「发现 XX 个 datetime.now()」这种机械统计，而是包含风险等级、修复策略、边界场景的完整报告——比如它发现了系统中部分表的历史数据已经被旧代码偷偷写成了本地时间、LLM 上下文中的时间提示词不应该被改成 UTC 这种只有通读全链路才能发现的隐性依赖。

这个调研阶段的产出，决定了我后面会不会返工。

### 第二步：规则——把架构决策变成 AI 读得懂的约束

有了调研报告，不是马上让 AI 改代码。我会先把关键决策写成规则文档放在 `docs/coding-rules/` 里——TRAE 的 agent 启动时会自动读取 `CLAUDE.md` 导航到这些规则，每条规则都在约束它什么能做、什么不能做。

最重要的经验是：**规则要写「边界」，不要写「位置」**。比如「边界层函数（API endpoint、LLM tool 的 execute 方法）负责时间格式转换，内部函数只处理一种格式」——这条规则不绑定到任何一个具体的文件名或函数名上，即使未来代码被重构，规则也不会腐烂。如果写成「改 lifeprism/xx/tools/yy.py 的 execute 方法」，三个月后函数挪了位置，规则就废了。

### 第三步：执行——分阶段派发，验证消费者而不仅是生产者

任务拆成 issue 之后，用 TRAE 的多个 agent 并行执行。但关键不是并行本身，而是**每个阶段完成后停下来验证**。

TRAE 支持 `/plan` 命令把任务分解为依赖步骤，我会在计划中加硬性拦截点：比如「第一阶段只改基础设施——完成后必须是真实调用验证（调用真实的 LLM 工具看输出有没有残留的 UTC 时间戳），不只是跑单元测试」。这帮我揪出了一个很隐蔽的 bug：所有代码看起来都对了，单元测试全过，但一个 LLM 工具的列表接口输出里仍然带着 `+00:00`——这种问题任何静态审查都发现不了。

另一个让我大幅提效的是**自动化浏览器测试**。Demo 最终是给评委在浏览器里体验的，前端交互的验证如果全靠手动点，改一行代码就要打开浏览器跑一遍流程，效率极低。TRAE 支持让 agent 直接在浏览器中执行操作并截图验证，我把高频验证场景（比如时区重构后日期选择器是否跨天错位、习惯打卡的日历热力图是否正确渲染）写成自动化的检查步骤交给 agent 跑。改完代码后一句指令，agent 自己打开页面、做交互、截图比对——我在旁边看着结果就行。**

TRAE 的终端能力在这里也很关键——我可以直接在同一个会话里跑端到端测试，让 agent 修正自己犯的错。

> 以上是个人实践中总结的工作流。下面是我具体用到的 TRAE 功能配置方式。

通过 TRAE 的智能体配置、文档管理和命令工具，实现高效的人机协同开发。核心思路是让 AI 能够理解项目上下文、遵循统一规则、产出符合需求的高质量成果，从而提高开发效率和代码质量。

1. 为不同模块设置独立智能体，实现上下文隔离

为不同模块设置专门的智能体，在提示词中为每个智能体设定专门的规则以及必须阅读的本地文档；为不同智能体配置不同的工具（内置工具和 MCP 工具）；实现不同智能体拥有独立的初始上下文环境。

**目的**：避免不同模块知识互相干扰，实现上下文隔离，让专门的任务使用专门的智能体，提升回答精准度和开发效率。

2. 打造为 AI 而生的项目上下文

在项目根目录添加 `AGENTS.md` 或 `CLAUDE.md` 作为总项目的导航地图，添加最基础的项目规则（不宜超过 200 行），包括文档体系总览、文档阅读规则和核心工程规则。

**目的**：让智能体快速理解项目结构和规则，减少人工解释成本，确保 AI 遵循统一的工程实践。

3. 构建结构化的 docs 文件夹

在 `docs/` 文件夹下放置以下目录：

- **`specs/`（产品规格文档）**：承载业务意图、业务规则、领域概念，以及规范性技术契约
- **`PRD/`（产品需求文档）**：描述产品的目标、用户需求和功能范围
- **`ADR/`（架构决策记录）**：记录对于长期具有重要作用的架构修改决定
- **`rules/`（规则文档）**：包含编码规范、文档编写规范等约束性规则
- **`history-bugs/`（历史 Bug 记录）**：存放可复用的 Bug 经验
- **`plans/`（执行计划）**：执行过程中的任务分解和执行记录

**目的**：为智能体提供结构化的知识体系，使其能够按需查找信息，同时保证项目知识的可追溯性和一致性。

4. 使用 `/spec` 命令设计规格文档

使用 TRAE 的 `/spec` 命令来设计当前需求的规格文档，明确功能的业务意图、核心规则和技术契约。

**目的**：建立需求与实现之间的明确契约，确保开发过程不偏离需求方向，为智能体提供清晰的实现边界。

5. 使用 `/plan` 命令设计执行计划

使用 TRAE 的 `/plan` 命令来设计如何执行任务，将大任务分解为多个可执行的子步骤，每个步骤都有明确目标。

**目的**：将复杂任务拆解为可控的子任务，提高开发过程的可管理性和可追踪性，便于智能体按步骤完成工作。

6. 在 `.agents` 目录下配置自定义 Skill

在 `~/.agents` 或项目目录下的 `./.agents` 中添加全局或项目专属的 skill，覆盖界面开发、接口实现、文档编写等不同领域。

**目的**：让智能体掌握项目特定的技能和知识，实现项目专属能力的复用，减少重复训练和人工调整成本。

7. 设计专门的 Hook 来约束智能体行为

在项目设置中配置专门的 Hook，在 AI 准备修改代码前触发规则检查，在 AI 完成任务后检查文档更新，设置自动化脚本在特定条件下运行测试或代码格式化。

**目的**：实现自动化质量保障，在关键节点约束智能体行为，确保 AI 生成的成果符合项目规范，减少人工审查工作量。
