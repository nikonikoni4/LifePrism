

# 重构goal界面和逻辑交互系统


## 为什么要做目标管理系统
回归第一性原理，为什么我要做这个目标管理系统，
1. 这个是一个数据写入，可以让ai知道我目前阶段正在做什么，让ai更好的理解我。 
2. 这个系统是ACT 承诺部分的一个下属分支，用来拓宽act的能力边界，更好的进行act的承诺部分，让我们改变有据可依，而不是仅仅停留在空想阶段，避免出现只沉浸于头脑承诺，或者个人思想进步但是行动停滞不前的陷阱 
3. 更一般的属性是让我们执行计划更加有条理。

具体内容：

1. 整体逻辑链条是承诺->目标->计划书(可选)->todo(todo下面有一个sub_todo,可以用来写一个具体的action之类的) 
2. 目标：采用SMART法则
3. 最主要的计划书：是一个思维缓冲带，从想法到落地行动是一个巨大的鸿沟，当我们有了想法但是想法没有写下来，大脑很难处理这么抽象的问题，导致行动受阻，很难安排计划，就有可能导致心情难受，甚至是拖延。基于我自己的经验，最好的办法就是把想法全部写下来，然后在组织逻辑编排，然后在迭代。所以计划书的作用是思维缓冲区。 
4. todo部分，是按照计划书中的[] 生成的（这里还有一些技术问题，暂时不讨论），然后计划放置在任务池中。


## 新架构：

1. 原plan改为计划书
    - 定义：计划书是思维缓冲区，是目标到执行层的一个重要缓冲地带。在物理层面就是一个md文档
    - 属性
        - 绑定的goal_id 
        - 状态：
            - 已完成
            - 进行中
            - 搁置（搁置之后，这个计划书与之相关的为完成的todo都变成搁置状态）
    - 功能：
        - 计划书的布局：计划书只有三个一级标题
            - '# 格式要求': 这个是为了计划书可以在别的ai应用中使用，为了别的应用不修改格式而写
            - '# 草稿'：用来随心记录
            - '# 正式': 正式记录。正式记录一般是由ai依据草稿生成的，用来理清楚
        - 可以从计划书中读取 md格式的[]来获取当前文档中的todo，然后转为当前项目中的todo。
            这里两个方案：
                - 1. 使用正则表达式扫描
                - 2. 使用ai扫描

    
2. todo的管理问题
    - 应该修改todo的属性：
        1. 完成状态（代码层面完成状态：✓）：
            - 未完成（已经安排了日期的todo）
            - 已完成
            - 搁置（在计划池中的状态）
        2. 完成时间（代码层面完成状态：✓）：当天或多天 
        3. 拖延日期（代码层面完成状态：×）：超出预计完成时间，则会显示拖延时长（天）
        4. 未完成原因拖延日期（代码层面完成状态：×）：需要写明原因
        5. sub_todo(代码层面完成状态：×)：可以用来写具体的action
        6. goal_id（代码层面完成状态：✓）：继承自计划书，后续可自行修改
        7. 其他当前所有的属性也保留，比如颜色等
    - 也就是需要增加：

        5. sub_todo(代码层面完成状态：×)：可以用来写具体的action

3. goal重构

        4. 当前投入时间（刷新页面时才更新）
        5. 绑定的类别
        6. 其他属性仍保留

## goal页面设计

### 搞清楚整体风格
1. 这个网站是工具属性的内容
2. 用户是用来制定计划，提高效率的
3. 用户一进来就应该能够快速找到所需要操作的内容。所以需要把一些重要的内容显示出来，尽量减少互动按键。

### 目标界面

1. 目标需要分类吗？
我觉得不需要，分类逻辑好像会变得更加麻烦。那那么在布局上就要按照目标的状态显示出目标。已完成和进行中。
2. 目标需要reward吗？
目标最大的reward应该是自己的改变，外在的奖励我觉得有点虚，至少我自己似乎不会这么用的。所以取消reward界面。
3. 如何设置进度界面呢？
    1. 保留目前的预设里程碑，达到中间目标
    2. 已投入时间（如果有监控的话）
    3. 已投入天数
    4. 用户自定义的进度界面，一个timeline，的显示内容，写下完成的心得
