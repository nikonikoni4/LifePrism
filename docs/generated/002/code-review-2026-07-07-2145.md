### Issue 1: 分页 `total` 返回当前页条数而非总记录数，分页功能完全失效
- **类型**: Performance / Architecture
- **置信度**: 100
- **位置**: `lifeprism/server/services/custom_records_service.py:134`；`frontend/apps/custom-records/components/TypeDetailView.tsx:172`
- **详情**: Aggregator 的 `query_entries` 只返回当前页记录列表（带 LIMIT/OFFSET），不返回总记录数。Service 用 `len(items)`（当前页条数）填充 `total` 字段。前端用此值计算 `totalPages = Math.ceil(total / pageSize)`，当记录数超过一页时（如 50 条、pageSize=20），`total=20`，`totalPages=1`，分页按钮永远不显示，用户无法翻页。
- **依据**: 代码确认 — `return CustomRecordEntryListResponse(items=items, total=len(items))`

```python
# custom_records_service.py:127-134
entries = custom_record_repository.query_entries(
    type_id=type_id, date_range=date_range, page=page, page_size=page_size,
)
items = [_convert_to_entry_item(e) for e in entries]
return CustomRecordEntryListResponse(items=items, total=len(items))  # 不是真实总数
```
```typescript
// TypeDetailView.tsx:172
const totalPages = Math.ceil(total / pageSize) || 1;  // total=20, pageSize=20 → 永远 1
```

### Issue 3: Service 层 `get_type` 未处理 repository 返回的 None，导致 500 错误
- **类型**: Best Practices
- **置信度**: 95
- **位置**: `lifeprism/server/services/custom_records_service.py:69-77`
- **详情**: `get_type_by_id` 返回类型为 `dict | None`，当类型不存在时返回 `None`。但 `get_type` 直接将结果传给 `_convert_to_type_item`，后者通过 `item["id"]` 访问字典键，传入 `None` 会抛出 `TypeError: 'NoneType' object is not subscriptable`。文档字符串声明抛出 `EntityNotFoundError`，但实际抛出 `TypeError`，API 返回 500 而非 404。
- **依据**: 代码确认 — `get_type_by_id` 可返回 None，`_convert_to_type_item` 直接做 `item["id"]`

```python
def get_type(type_id: str) -> CustomRecordTypeItem:
    type_dict = custom_record_repository.get_type_by_id(type_id)  # 可能返回 None
    fields = custom_record_repository.get_type_fields(type_id)
    return _convert_to_type_item(type_dict, fields)  # None["id"] → TypeError
```

### Issue 6: Service 层冗余查询字段定义

### Issue 7: `handleFilter` 双重请求且使用过期 page 值
- **类型**: Performance / Code Quality
- **置信度**: 90
- **位置**: `frontend/apps/custom-records/components/TypeDetailView.tsx:98-101`
- **详情**: `handleFilter` 先 `setPage(1)` 再立即调用 `loadData()`。`setPage` 是异步的，`loadData` 闭包捕获的是旧的 `page` 值，所以直接调用用的是旧页码发起请求。同时 `page` 变化让 `loadData`（useCallback 依赖 page）重建，触发 `useEffect` 再发一次请求（用新 page=1）。结果：筛选时产生两次请求，第一次用旧页码（可能越界），第二次才正确，且两次响应可能乱序到达。
- **依据**: React useCallback/useEffect 机制确认

```typescript
const handleFilter = () => {
    setPage(1);     // 异步，未生效
    loadData();      // 闭包用旧 page，且 useEffect 会再触发一次
};
```

### Issue 9: debounce 定时器未在组件卸载时清理，存在资源泄漏
- **类型**: Performance
- **置信度**: 85
- **位置**: `frontend/apps/custom-records/components/TypeDetailView.tsx:104-120`
- **详情**: `handleTemplateChange` 使用 `debounceRef.current = setTimeout(...)` 实现 debounce 自动保存，但组件没有 `useEffect` 清理函数来清除未执行的 timeout。如果用户切换模板后立即返回（组件卸载），timeout 回调仍会执行，尝试在已卸载组件上调用 `setSaveStatus` 和发起 API 请求。内部还有一层 1500ms 的 setTimeout 也会泄漏。
- **依据**: React hooks 最佳实践 — 定时器必须在 useEffect cleanup 中清理

```typescript
const debounceRef = React.useRef<ReturnType<typeof setTimeout> | null>(null);
// 缺少：
// useEffect(() => { return () => { if (debounceRef.current) clearTimeout(debounceRef.current); }; }, []);
```

class UpdateTypeConfigRequest(BaseModel):
