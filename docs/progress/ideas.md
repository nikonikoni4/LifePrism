### 💭 2026-07-16 数据库删除操作无法被同步感知

- **来源**：用户直接输入
- **类型**：问题
- **状态**：💭 待确认
- **内容**：当前数据库操作无法记录删除操作（没有 delete log / tombstone 机制），导致同步时如果本端删除了某条数据，另一端无法感知到删除动作，Pull 阶段会将该数据重新同步过来，形成"删不掉"的问题。
- **背景**：同步机制基于 `updated_at` LWW 比较和文件目录全量快照（#39），对新增和修改能正确处理；但物理删除后数据库层面没有任何痕迹残留，同步端无法区分"本端删过"和"从未有过"。
- **讨论点**：
  - 方案：软删除（加 `deleted_at` 字段 + 过滤查询）vs 删除日志表（`deleted_records` 记录已删除 ID）vs 全局 tombstone 表
  - 需要考虑自定义动态表（custom_*）和内置表（mood_entries 等）的统一处理
  - tombstone 的清理策略：多久后可以物理删除？
  - 是否影响现有的 LWW 冲突解决逻辑？

### 💭 2026-07-15 优化 user.md 全量加载导致 AI 对话上下文过长

- **来源**：用户直接输入
- **类型**：需求
- **状态**：💭 待确认
- **内容**：当前每次 AI 对话都会全量加载 `localData/user/user.md`（约 12KB/57 行），内容随使用持续增长已特别长，导致每次对话上下文过长、token 浪费。需要优化加载策略。
- **背景**：`user.md` 包含用户基本信息、社会关系、价值观、核心偏好、习惯禁忌等，由 AI agent 通过 `lifeprism/llm/agent/context.py` 等模块加载到对话上下文。内容由 dreaming task 等流程持续追加，体积只会越来越大。
- **讨论点**：
  - 优化方向待定：分段按需加载？摘要 + 详情分层？定期压缩归档？
  - 是否需要区分"每次必读的核心信息"与"按场景加载的详细信息"
  - 与 dreaming task 写入逻辑的关系（写入策略是否也需要调整）

### 💭 2026-07-16 云端同步多表独立请求性能优化

- **来源**：用户直接输入
- **类型**：观察
- **状态**：💭 待确认
- **内容**：当前云端同步时，每个表都会单独发起一个 HTTP 请求来拉取数据。单次请求约 25ms，表多了之后整体耗时线性累积，同步速度较慢。考虑是否存在优化空间，例如将多表请求合并为一次批量拉取。
- **讨论点**：
  - 是否需要优化？当前场景下表数量级是多少，实际同步总耗时还没有确切统计
  - 优化方案方向：后端提供批量接口（一次请求拉取多表）？前端并发请求（Promise.all）减少串行等待？
  - 需要先测量当前实际耗时数据，再决定是否投入优化
