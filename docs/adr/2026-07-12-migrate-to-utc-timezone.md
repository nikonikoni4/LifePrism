# 迁移到 UTC 时区和 ISO 8601 格式

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

系统当前使用本地时区（主要是 `datetime.now()`）存储时间数据，导致多个严重问题：

1. **时区不一致**：旧迁移遗留的 3 个字段使用 UTC，其他 80+ 字段使用本地时区，导致 LWW 冲突解决失败
2. **前后端不一致**：前端部分代码使用 UTC，后端使用本地时间，数据同步时时间戳比较错误
3. **时间格式混乱**：同一表内混合使用标准格式（`YYYY-MM-DD HH:MM:SS`）和 ISO 格式（`YYYY-MM-DDTHH:MM:SS.ffffff`）
4. **部署风险**：如果云端服务器部署在海外（如 UTC 时区），本地和云端时间戳将错位 8 小时

这些问题在 `docs/known-limitations/timezone-and-format-inconsistency.md` 中有详细记录。

### 讨论范围

本次决策覆盖：
- 时区策略：本地时区 vs UTC
- 时间格式：标准格式 vs ISO 8601
- 数据存储：数据库字段的存储格式
- API 传输：前后端数据交换格式
- 前端处理：Date 对象的使用方式

本次决策需要回答的关键问题：
- 是否采用业界最佳实践（UTC + ISO 8601）？
- 如何处理历史数据迁移？
- 前后端如何统一时区处理？

### 非讨论范围

- 具体的代码修改方案（后续规划）
- 历史数据迁移的具体执行步骤（后续规划）
- 前端时间展示的格式化方案（展示层细节）

### 模糊信息的明确定义

- **本地时区**：在本文中指使用 `datetime.now()`（无时区信息）或 `datetime('now', 'localtime')`，依赖系统时区设置
- **UTC**：在本文中指使用 `datetime.now(timezone.utc)` 或 `datetime('now')`（SQLite）生成的带时区信息的时间
- **ISO 8601 格式**：`YYYY-MM-DDTHH:MM:SS.ffffff+00:00` 或 `YYYY-MM-DDTHH:MM:SS.ffffffZ`
- **标准格式**：`YYYY-MM-DD HH:MM:SS`（无时区标识）

### 问题深度

这是涉及**架构原则和长期维护**的深层决策：
- 影响数据存储格式（难以回退）
- 影响前后端协议（需同步修改）
- 影响历史数据（需迁移）
- 影响未来扩展性（跨时区部署）

## 现状

### 当前实现

**后端**：
- 80+ 张表使用本地时区（`datetime.now()`）
- 3 张旧表使用 UTC（遗留问题）
- 同步模块部分代码使用 UTC
- 时间格式混合：68% 标准格式，3% ISO 格式

**前端**：
- 27 处违规使用 `.toISOString()`（UTC）
- 部分代码使用 `toLocalDateTimeString()`（本地时间）

**数据库**：
- SQLite TEXT 类型存储时间字符串
- 大部分表使用 `datetime('now', 'localtime')` 作为 DEFAULT

### 历史原因

**为什么当初选择本地时区**：

1. **调试方便**：数据库中的时间可以直接阅读，与本地时钟一致
2. **桌面应用假设**：认为这只是本地桌面应用，不需要考虑跨时区
3. **手写同步代码**：数据同步是手写的，简单使用本地时间戳比较
4. **知识局限**：当时对时区最佳实践不了解，不知道 UTC 的必要性
5. **避免复杂性**：担心 UTC 引入额外复杂度

### 现有问题

**P0 问题**（严重）：
- 数据同步 LWW 冲突解决失效（时区不一致导致字符串比较错误）
- 前端日期字段错位一天（UTC+ 时区午夜前后）

**P1 问题**（高优先级）：
- 同一表内时间格式不一致
- 时间排序和范围查询可能出错

**未来风险**：
- 云端部署到海外服务器时数据完全错位
- 无法支持跨时区用户
- 夏令时问题（如果未来扩展到有夏令时的地区）

### 不能忽略的约束

1. **历史数据**：已有数据使用本地时区，需要迁移
2. **前后端同步**：必须同时修改，否则问题更严重
3. **兼容性**：现有 API 消费者可能依赖当前格式
4. **测试覆盖**：时间相关逻辑测试较少，改动风险大

## 可选方案

### 方案 A：保持现状（本地时区）

维持当前的本地时区策略，仅修复格式不一致问题。

**优势**

- 不需要大规模修改代码
- 数据库时间可读性好（与本地时钟一致）
- 不需要迁移历史数据
- 调试时直观

**劣势**

- 无法解决时区不一致问题（旧表仍是 UTC）
- 云端部署到海外时数据错位
- 无法支持跨时区用户
- 夏令时风险
- 违反业界最佳实践（Laravel、Spring Boot、FastAPI 等都推荐 UTC）
- ActivityWatch 等成熟项目也使用 UTC，证明桌面应用也需要 UTC

### 方案 B：迁移到 UTC + ISO 8601（推荐）

统一使用 UTC 时区和 ISO 8601 格式。

**优势**

- 符合业界最佳实践（所有主流框架推荐）
- 解决时区不一致问题（统一为 UTC）
- 支持未来扩展（跨时区部署、跨时区用户）
- 避免夏令时问题
- 数据导出/导入标准化（ISO 8601 是国际标准）
- 前后端协议清晰（带时区标识）
- 与成熟项目（ActivityWatch）一致

**劣势**

- 需要大规模修改代码（约 100+ 处）
- 需要迁移历史数据
- 数据库时间可读性下降（需要手动转换）
- 测试和验证工作量大
- 前后端必须同步修改

### 方案 C：混合策略（不推荐）

数据库使用本地时区，API 传输时转换为 UTC。

**优势**

- 数据库可读性好
- API 符合标准

**劣势**

- 转换逻辑复杂，容易出错
- 仍然无法解决旧表 UTC 和新表本地时区的不一致
- 服务器迁移时仍有风险
- 违反"统一存储 UTC"的最佳实践

## 最终决策

选择**方案 B：迁移到 UTC + ISO 8601**。

## 决策原因

### 1. 解决现有严重问题

当前的时区不一致已经导致数据同步失败（LWW 比较错误），这是 **P0 级别问题**，必须解决。方案 A 无法解决，只有方案 B 可以彻底解决。

### 2. 符合业界最佳实践

调研结果显示：
- Laravel、Spring Boot、FastAPI、Django 等所有主流框架都**强烈推荐 UTC**
- ActivityWatch（监控本地活动的桌面应用）也使用 UTC，证明**即使是桌面应用也需要 UTC**
- 业界共识："默认用 UTC，除非有特殊理由"，而不是"有跨时区需求才用 UTC"

### 3. 未来扩展性

虽然当前只是桌面应用，但：
- 已经有云端同步功能（可能部署到海外服务器）
- 用户可能旅行或更换设备（跨时区使用）
- 未来可能扩展到 Web 版、移动版
- 现在不改，未来成本更高

### 4. 避免技术债累积

当前问题已经很严重（时区不一致、格式混乱），如果继续使用本地时区，技术债会越来越大，最终不得不重构时代价更高。

### 5. 一次性解决所有问题

迁移到 UTC 可以同时解决：
- 时区不一致
- 格式混乱
- 前后端不一致
- 未来扩展性

### 6. 成本可控

虽然修改工作量大，但：
- 问题域清晰（时间字段已全部排查）
- 修改模式统一（`datetime.now()` → `datetime.now(timezone.utc)`）
- 可以分阶段执行（先修代码，再迁历史数据）
- 有测试保障（单元测试 + 集成测试）

## 后续影响

### 代码层面

**需要修改**：
- 后端：约 100+ 处 `datetime.now()` → `datetime.now(timezone.utc)`
- 后端：约 10 处 `.isoformat()` 统一使用（替换 `.strftime()`）
- 前端：27 处违规代码修复
- 数据库：所有表的 DEFAULT 改为 `datetime('now')`（SQLite UTC）

**影响模块**：
- `lifeprism/providers/` - 所有 Provider
- `lifeprism/server/api/` - 所有 API
- `frontend/src/` - 时间相关组件
- 数据库迁移脚本

### 数据层面

**历史数据迁移**：
- 需要将所有本地时间字段转换为 UTC
- 策略：假设历史数据都是 UTC+8（北京时间），统一减 8 小时
- 风险：如果历史数据有异地生成的，可能不准确（但当前没有异地用户）

### 用户体验

**无影响**：
- 前端展示层自动转换为本地时区（Date 对象自动处理）
- 用户看到的时间与之前一致

### 运维部署

**好处**：
- 云端可以部署到任意地区的服务器
- 不依赖服务器时区设置
- 数据备份和恢复更安全

### 文档更新

**需要更新**：
- API 文档：说明时间格式为 ISO 8601 + UTC
- 开发规范：明确禁止使用 `datetime.now()`，必须用 `datetime.now(timezone.utc)`
- 已知限制文档：迁移完成后移除时区相关限制

### 测试验证

**需要验证**：
- 数据同步功能（LWW 冲突解决）
- 时间范围查询
- 时间排序
- 前端时间显示
- 跨时区场景（模拟服务器在不同时区）

### 风险和缓解

**主要风险**：
1. **历史数据迁移错误**
   - 缓解：先在测试环境验证，备份生产数据
2. **前后端不同步导致功能异常**
   - 缓解：在同一版本中同时发布前后端改动
3. **遗漏修改点**
   - 缓解：已有完整的时间字段清单（`docs/generated/`）

**回退方案**：
- 保留历史数据备份
- 第一个版本可以支持双格式读取（兼容模式）
- 验证通过后再移除兼容代码
