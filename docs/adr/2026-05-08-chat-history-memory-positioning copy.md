## 问题界定

### 问题简述

在 LifePrism 记忆系统中，是否需要 `chat_history.md` 作为独立文档？如果需要，它的定位、结构和更新机制是什么？与已有的 `behavior.md` 如何划分职责？

### 讨论范围

- `chat_history.md` 在记忆系统中的定位
- `chat_history.md` 的结构设计与更新机制
- `chat_history.md` 与 `behavior.md` 的数据流关系

### 非讨论范围

- `behavior.md` 本身 4 个组成部分（日记总结/行为总结/心情总结/聊天总结）的具体结构
- 其他记忆文档（`growth_story.md`、`cognition.md`、`emotion.md` 等）的实现细节
- 间隔任务的触发周期参数（具体小时数）与技术实现细节

### 关键概念明确

**定时任务 vs 间隔任务**：

- **定时任务**：在特定时间点执行（如每天凌晨 4:00）
  - 适用场景：需要基于「完整一天数据」进行综合总结的场景
  - 典型代表：`behavior.md` 的每日总结
- **间隔任务**：按固定时间间隔重复执行（如每隔若干小时一次）
  - 适用场景：需要保持数据新鲜度、服务于实时对话上下文的场景
  - 典型代表：`chat_history.md` 的增量写入

### 问题深度

本决策同时涉及浅层与深层：

- **浅层**：`chat_history.md` 的结构格式（section 划分、写入内容）
- **深层**：记忆系统分层中，为什么需要独立的「短期跨会话上下文层」，以及它与「每日综合总结层」的时间粒度差异

## 现状（当前的问题）

### 问题背景

LifePrism 记忆系统采用四层架构：

```
原始数据层 | 最近状态 -> 叙事层 -> 心理建模层 -> 心智进化层
```

在原始数据层中，已有 `behavior.md` 用于记录用户每天的行为语义，包含 4 个组成部分：

1. 日记总结
2. 行为总结（从 user_note、ai_note、客观行为数据中总结）
3. 心情总结（从心情数据与聊天数据中总结）
4. 聊天总结（存放最近对话都说了什么，以 session_id 为 key 存放）

### 核心矛盾

在设计 `behavior.md` 的聊天总结部分时，发现了一个时间粒度冲突：

1. **行为总结和心情总结**：需要按天总结
   - 原因：ai_note（截图分析）需要计算时间密度分段，保持时间连续性
   - 更新机制：定时任务（每天凌晨执行）

2. **聊天总结**：需要跨会话连贯性
   - 原因：用户可能在多个 session 中持续讨论同一话题（如项目推进、心理困扰）
   - 问题：如果按天切割，会破坏对话的连续性，导致 AI 每次对话都需要重新建立上下文

### 具体问题

1. **上下文断裂**：用户在今天 10:00 开始讨论某个设计问题，下午 15:00 继续讨论，如果只有按天总结的 `behavior.md`，AI 在 15:00 的对话中无法快速获取 10:00 的讨论内容

2. **数据重复**：聊天记录中可能包含行为信息（"今天写了 XXX 代码"）和心情信息（"感到焦虑"），如果在聊天总结中完整记录，会与行为总结、心情总结重复

3. **溯源困难**：`behavior.md` 的聊天总结需要能追溯到原始 session，但如果直接在 `behavior.md` 中存储所有 session 详情，会导致文件过大

## 可选方案

### 方案 A：不创建 chat_history.md，在 behavior.md 中直接处理

**结构**：

```markdown
## YYYY-MM-DD

### 日记总结
...

### 行为总结
...

### 心情总结
...

### 聊天总结
session_id_1: [主题] [关键内容]
session_id_2: [主题] [关键内容]
```

**优势**：
- 结构简单，所有原始数据都在一个文件中
- 不需要额外的间隔任务

**劣势**：
- 无法提供跨会话上下文（今天的对话无法快速关联昨天的讨论）
- 按天切割会破坏持续话题的连贯性
- AI 每次对话开始时需要读取多天的 `behavior.md` 才能建立完整上下文，成本高

### 方案 B：创建 chat_history.md 作为短期上下文层

**结构**：

```markdown
---
name: chat_history
summary: 近期对话的跨会话上下文，按天组织
read_priority: high
last_updated: YYYY-MM-DD
---

# YYYY-MM-DD

## 对话摘要
### session_id_1
**主题**: 讨论 LifePrism 记忆系统设计
**关键内容**: 
- 用户质疑 chat_history 的必要性
- 讨论了 behavior 的四个组成部分
- 确定聊天需要跨会话连贯性

**情感标记**: 思考、困惑 → 清晰
**待流入**: growth_story.md (设计决策过程)

### session_id_2
...

## 持续话题
- **LifePrism 记忆系统重构**: session_id_1, session_id_2 (2026-05-08 ~ 今天)
- **XXX 项目推进**: session_id_3 (2026-05-06 ~ 今天)
```

**更新机制**：
- 间隔任务：每隔若干小时查询新增/更新的 session，写入对应日期的 section
- 按天组织，但不删除历史内容

**与 behavior.md 的关系**：
- `behavior.md` 每天定时更新时，从 `chat_history.md` 读取昨天的对话摘要
- 写入 `behavior.md` 的聊天总结部分时，避免与行为总结、心情总结重复（只提及或完全不提已有内容）

**优势**：
1. **解决跨会话连贯性**：通过"持续话题"部分，AI 可以快速看到用户最近在持续关注什么
2. **提供短期上下文**：AI 对话开始时优先读取 `chat_history.md`（read_priority: high），快速建立上下文
3. **避免数据重复**：`chat_history.md` 存储详细的对话摘要，`behavior.md` 只存储去重后的聊天总结
4. **溯源清晰**：通过 session_id 可以追溯到原始对话
5. **职责分离**：
   - `chat_history.md`：短期、高频读取、跨会话连贯性
   - `behavior.md`：长期、按需查询、每日综合总结

**劣势**：
- 需要额外的间隔任务维护
- 增加了一个文档，系统复杂度略有提升

## 最终决策

**采用方案 B：创建 `chat_history.md` 作为记忆系统的「短期跨会话上下文层」**

### 决策原因

#### 1. 解决核心矛盾：时间粒度差异

- **行为/心情总结**：需要按天总结（保持时间连续性）
- **聊天总结**：需要跨会话连贯性（保持话题连续性）

这两种需求的时间粒度不同，强行合并到 `behavior.md` 会导致：
- 要么牺牲行为/心情的时间连续性（改为间隔更新）
- 要么牺牲聊天的话题连贯性（按天切割）

独立的 `chat_history.md` 可以用不同的更新机制（间隔任务）服务于不同的需求。

#### 2. 提升 AI 对话体验

用户在多个 session 中持续讨论同一话题时，AI 需要快速建立上下文。如果只有按天总结的 `behavior.md`：

- AI 需要读取多天的 `behavior.md` 才能找到相关讨论
- 无法快速识别"持续话题"

`chat_history.md` 的"持续话题"部分可以让 AI 在对话开始时立即知道：
- 用户最近在关注什么
- 哪些话题跨越了多个 session
- 相关讨论的 session_id 列表

#### 3. 避免数据重复与冗余

聊天记录中可能包含行为信息和心情信息，如果在 `behavior.md` 中完整记录，会导致重复。

通过分层：
- `chat_history.md`：存储详细的对话摘要（包含所有内容）
- `behavior.md`：从 `chat_history.md` 读取后，只写入不重复的部分

这样既保留了完整信息（在 `chat_history.md` 中），又避免了冗余（在 `behavior.md` 中）。

#### 4. 符合记忆系统的分层原则

记忆系统的核心原则是"层与层之间单向流动"：

```
chat_history.md (短期上下文) → behavior.md (每日总结) → 心理建模层
```

- `chat_history.md`：原始数据层的"短期缓冲区"
- `behavior.md`：原始数据层的"长期档案"

这种分层符合"渐进式披露"的设计原则：
- 高频读取：`chat_history.md`（每次对话开始）
- 低频读取：`behavior.md`（按需查询历史）

### 实施细节

#### 文档位置
`templates/user/daily_data/chat_history.md`

#### 更新机制
- **间隔任务**：每隔若干小时执行一次
- **写入逻辑**：
  1. 查询最近一个间隔内新增/更新的 sessions
  2. 对每个 session 生成摘要（主题、关键内容、情感标记、待流入标记）
  3. 写入对应日期的"对话摘要"部分
  4. 更新"持续话题"部分（检测跨 session 的话题）

#### 与 behavior.md 的数据流
- **时机**：`behavior.md` 每天定时更新时
- **读取**：从 `chat_history.md` 读取昨天的对话摘要
- **写入**：写入 `behavior.md` 的"聊天总结"部分，但避免与"行为总结"、"心情总结"重复（只提及或完全不提已有内容）

#### 生命周期
- 按天组织内容，不删除历史记录
- 长期保留，作为可溯源的原始数据
