# Prompt 集中管理方案决策

## 版本历史

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0  | 创建文档初稿 |

## 问题界定

### 问题简述

项目中存在多个 LLM prompts 散落在各个函数中（如 `agent_schedule_job.py`），需要确定一个统一的管理方案。

### 讨论范围

- 为什么需要集中管理 prompt
- 选择什么方式管理 prompt（纯代码 vs 文件）
- 如果选择文件管理，为什么选择 Markdown 格式
- 如何解决纯代码方案的主要缺点

### 非讨论范围

- 具体的代码实现细节
- 命名规范（文件命名、函数命名等）
- 文件格式的技术细节（YAML 语法、解析逻辑等）
- Loader 的具体实现

### 问题深度

这是一个架构设计决策，影响：
- 项目的可维护性
- Prompt 的迭代效率
- 团队协作方式
- 未来的扩展性

## 现状分析

### 当前问题

1. **Prompt 散落各处**：
   - 每个函数内部定义自己的 prompt
   - 难以统一查看和管理
   - 修改需要在代码中查找

2. **缺乏版本管理**：
   - 修改 prompt 后无法追溯历史版本
   - 不知道哪个版本产生了哪些结果
   - 效果变差时难以回滚

3. **无法 A/B 测试**：
   - 只能使用一个版本的 prompt
   - 对比不同版本需要频繁修改代码

4. **代码耦合严重**：
   - Prompt 和业务逻辑混在一起
   - 修改 prompt 需要重启服务
   - 非技术人员无法参与 prompt 优化

## 可选方案

### 方案 A：纯代码方式（初始方案）

**描述**：
- 在 `lifeprism/llm/prompts/` 目录下创建 Python 文件
- 使用函数返回 prompt 字符串
- 支持参数化注入

**优点**：
- 简单直接，无需额外解析
- 类型安全，有 IDE 支持
- 不依赖外部文件格式
- 学习成本低

**缺点**：
1. **缺乏版本管理**：只能通过 Git 追溯，无法在代码中直接看到历史版本
2. **无法 A/B 测试**：同时使用多个版本需要写多个函数
3. **代码耦合**：修改 prompt 需要重启服务
4. **缺少元数据**：无法记录创建时间、修改原因等信息
5. **难以做效果评估**：没有关联 prompt 版本和输出结果
6. **缺少使用统计**：不知道哪些 prompt 被频繁使用

### 方案 B：文件管理方式（最终方案）

**描述**：
- 使用 Markdown 文件存储 prompt
- 一个文件包含一个模块的多个 prompts
- 每个 prompt 可以有多个版本
- 使用 YAML frontmatter 存储元数据
- Loader 负责加载和解析

**优点**：
- ✅ 版本管理：文件内可以保留多个版本，便于对比
- ✅ A/B 测试：通过参数指定版本即可
- ✅ 解耦：修改文件不需要重启服务（可选实现热加载）
- ✅ 元数据：记录创建时间、修改原因
- ✅ 使用统计：Loader 可以记录使用次数
- ✅ 便于协作：非技术人员也可以编辑 Markdown
- ✅ 与项目一致：项目中已有大量 md 文档作为 prompt（user.md, agent.md）

**缺点**：
- 需要实现 Loader 解析逻辑
- 增加了一层抽象
- 需要定义文件格式规范

### 方案 C：专业 Prompt 管理平台

**描述**：
- 使用 Latitude、PromptWorks 等开源平台
- 提供 Web UI 管理界面
- 自动化测试和评估

**优点**：
- 功能完善（版本管理、A/B 测试、效果评估等）
- Web UI 便于协作
- 自动化能力强

**缺点**：
- 需要额外部署服务
- 学习成本高
- 对于当前项目规模（< 20 个 prompts）过于复杂
- 增加系统复杂度

## 最终决策

**选择方案 B：文件管理方式（Markdown + YAML）**

## 决策原因

### 1. 为什么需要集中管理

**核心动机**：
- 项目中 prompt 数量逐渐增多（当前 4 个，未来可能 20+）
- Prompt 是 AI 应用的核心资产，需要像代码一样管理
- 需要追踪 prompt 的演进历史和效果

**具体原因**：
- **可维护性**：集中管理便于查找和修改
- **可追溯性**：需要知道每个版本的改动原因和效果
- **可测试性**：需要对比不同版本的效果
- **协作性**：团队成员需要共同优化 prompt

### 2. 为什么选择文件管理而非纯代码

**决策过程反思**：

在初始讨论中，AI 提出了纯代码方案并列出了优点，但**没有主动提供缺点分析**。这是一个重要的教训：
- 评估方案时，优点和缺点同等重要
- 只看优点容易做出片面决策
- 需要主动追问"这个方案有什么问题"

**追问缺点后的发现**：

纯代码方案有 12 个明显缺点，其中最关键的是：
1. 缺乏版本管理
2. 无法 A/B 测试
3. 代码耦合严重
4. 缺少元数据

这些缺点在项目发展中会逐渐暴露，早期解决比后期重构成本更低。

**文件管理的核心优势**：

通过将 prompt 存储在文件中，可以解决纯代码方案的前 3 个核心问题：
- **版本管理**：文件内保留多个版本，Git 追踪变更
- **A/B 测试**：Loader 支持指定版本加载
- **解耦**：修改文件不需要改代码，可选热加载

### 3. 为什么选择 Markdown 格式

**关键考虑**：

1. **与项目一致**：
   - 项目中已有 user.md、agent.md 等作为 prompt
   - 保持统一的文档风格

2. **编写体验**：
   - Markdown 是为文本设计的，编写 prompt 最自然
   - 支持语法高亮和预览
   - 便于 review 和对比

3. **灵活性**：
   - YAML frontmatter 存储元数据
   - 正文部分结构化存储多个 prompts 和版本
   - 易于扩展

4. **可读性**：
   - 直接在 GitHub/编辑器预览
   - 非技术人员也能理解和编辑

### 4. 为什么选择按模块分组

**初始考虑**：一个文件一个 prompt

**问题**：如果有 50 个 prompt，就是 50 个文件，管理成本高

**最终决策**：按大模块分组
- 初期：一个模块文件包含多个相关 prompts（如 `schedule_prompts.md` 包含 4 个 prompts）
- 扩展：当某个模块 prompts > 10 个时，再细分子模块

**原因**：
- 平衡了文件数量和管理复杂度
- 相关 prompts 集中，便于浏览
- 保留了未来拆分的灵活性

### 5. 针对性解决的缺点

基于 AI 提出的 12 个缺点，我们针对性解决了以下问题：

**已解决**：
- ✅ 问题 1：版本管理（文件内多版本 + Git）
- ✅ 问题 2：A/B 测试（Loader 支持指定版本）
- ✅ 问题 3：代码耦合（文件存储，可热加载）
- ✅ 问题 4：缺少元数据（metadata 部分记录创建时间、修改原因）
- ✅ 问题 10：缺少使用统计（usage_stats.yaml）

**暂不解决**：
- ❌ 问题 5：难以做效果评估（需要更复杂的系统，当前阶段不是重点）
- ❌ 问题 6：长 prompt 可读性（通过合理的章节划分缓解）
- ❌ 问题 7：缺少组合能力（当前 prompt 数量少，暂不需要）
- ❌ 问题 8：参数验证不足（可以后续添加）
- ❌ 问题 9：测试覆盖不全面（可以后续完善）
- ❌ 问题 11：多语言支持（项目只面向中文用户）
- ❌ 问题 12：缺少变量校验（可以后续添加）

**决策原则**：
- 优先解决影响最大的问题（版本管理、A/B 测试、代码耦合）
- 保持方案简单，避免过度设计
- 为未来扩展留有余地

## 决策影响

### 正面影响

1. **提升可维护性**：prompt 集中管理，便于查找和修改
2. **支持快速迭代**：可以方便地测试不同版本的 prompt
3. **降低耦合度**：prompt 和代码分离，修改更灵活
4. **便于协作**：非技术人员也可以参与 prompt 优化
5. **积累经验**：版本历史和修改原因成为宝贵的知识资产

### 潜在风险

1. **增加复杂度**：需要实现 Loader 和解析逻辑
2. **学习成本**：团队需要学习新的文件格式规范
3. **维护成本**：需要维护文件格式的一致性

### 风险缓解

- 提供清晰的文档和示例
- 实现简单的 Loader，避免过度设计
- 在实践中逐步完善规范

## 经验教训

### 关于 AI 辅助决策

**教训**：AI 提供方案时，需要主动追问缺点

**原因**：
- AI 倾向于展示方案的优点
- 缺点往往需要主动追问才会提供
- 只看优点容易做出片面决策

**改进**：
- 评估任何方案时，都要问"这个方案有什么问题"
- 对比多个方案时，要求列出优缺点对比表
- 重要决策要经过"优点 → 缺点 → 权衡"的完整流程

### 关于方案选择

**教训**：简单方案不一定是最好的方案

**原因**：
- 纯代码方案看起来简单，但隐藏了很多问题
- 这些问题在项目发展中会逐渐暴露
- 早期投入一些复杂度，可以避免后期重构

**改进**：
- 评估方案时，要考虑项目的发展阶段
- 当前简单 ≠ 长期简单
- 适度的前瞻性设计是必要的
