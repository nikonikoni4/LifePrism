# User Design Summary

## 目的

记录用户在重大设计决策中的偏好、判断方式和风险倾向，为后续 agent 自主决策提供参考，也为用户复盘决策方式提供材料。

| 2026-07-09 | [同步原子性策略](.\2026-07-09-sync-atomicity-strategy.md) | 用户在讨论同步错误处理粒度时，主动分析了 row-level best-effort 的致命缺陷——时间戳推进后失败行会永久丢失。用户判断依据是"整体的原子性才对"，认为 last_sync_time 应该代表"所有表已成功同步至此"的语义。 | 适用于涉及数据同步、增量查询、时间戳驱动重试的场景。用户会从"失败后能否恢复"的角度评估策略，而非仅看正常流程。 | 整体原子性会导致成功表重复同步（幂等但浪费资源）。如果同步表数量大幅增加或单次同步耗时长，可能需要重新评估"table-level 容错 + last_sync_time 整体原子"的优化方案。 |

| 2026-07-09 | [冲突解决策略](.\2026-07-09-lww-conflict-resolution.md) | 用户否决 CRDT 和版本号方案的核心依据是"表更改的内容太多"和"使用频率不高，存在较大时间差"。用户从实际使用场景出发判断冲突概率，而非从理论模型出发。2026-07-14 补充了三个可校验的决策前提——前提 1（主备模式）、前提 2（NTP 时钟偏差可控）、前提 3（主备切换间隔大于时钟偏差），并明确记录了每个前提失效时的备选切换路径。用户特别强调前提 3 的作用：即使云端时钟慢于本机，只要切换间隔覆盖偏差，LWW 的时间戳比较仍然正确。 | 适用于涉及冲突解决、并发控制等理论方案选择时，用户会从实际使用模式出发评估必要性，而非追求理论上的完备性。用户对"决策前提可校验"有明确要求——每条前提必须能在未来重新验证是否仍然成立。 | 这种"从使用场景倒推技术方案"的方式在 MVP 阶段是合理的，但如果使用模式变化（如多端同时编辑），需要重新评估。三个前提已将失效条件显式化（决策逻辑表），后续 agent 在修改同步相关代码前应先验证前提是否仍然成立，而非假设"LWW 永远是对的"。 |

| 2026-07-09 | [cloud_init.yaml 初始化策略](.\2026-07-09-cloud-init-atomic-strategy.md) | 用户在配置初始化策略上选择"验证失败不删除"，核心关注点是"密钥不可恢复"——密钥由本地 keyring 生成，删除文件后如果本地程序已关闭则无法重新获取。 | 适用于涉及不可恢复资源（密钥、token 等）的处理策略。用户对"不可恢复"有清醒认知，倾向于保留而非删除。 | 无重大风险，"保留文件方便重试"是合理的防御性策略。 |
| 2026-07-12 | [迁移到 UTC 时区和 ISO 8601 格式](.\2026-07-12-migrate-to-utc-timezone.md) | 用户主动承认历史技术债——当初选择本地时区是基于"调试方便"、"桌面应用不需要那么复杂"、"对最佳实践不了解"等原因。在了解业界最佳实践（Laravel/ActivityWatch 等都强制 UTC）和现有问题（时区不一致导致数据同步失败）后，选择迁移到 UTC。用户对"即使桌面应用也需要 UTC"的认知转变来自具体案例（ActivityWatch）而非理论说教。 | 适用于用户对历史决策有清醒认知、愿意承认知识局限、并在有充分证据时修正方向的场景。用户的决策转变依赖于"具体案例 + 现有问题"的双重驱动，而非单纯的理论最佳实践。 | 迁移成本大（100+ 处代码 + 历史数据），但用户已接受。需注意用户对"最佳实践"的认可是基于"已出现问题 + 同类项目案例"，而非预防性采纳。后续 agent 在推荐最佳实践时，应结合"当前痛点 + 具体案例"，而非仅引用官方文档。 |
| 2026-07-12 | [时间转换职责分层架构](.\2026-07-12-time-conversion-layering.md) | 用户在决策过程中经历了明显的动摇：先是质疑"一层层过滤"是否合理，一度想改 Repository 层增加 `return_local_time` 参数（因为"修改点较多且容易出错"），又主动提出装饰器方案（想减少重复代码），并要求"派出 agent 审查是否合理"。审查报告指出装饰器的静默失败、字段用途差异等风险后，用户确认回到原方案。用户在动摇时会主动寻求外部审查，而非固执己见。 | 适用于用户对架构方案有动摇时，会主动提出替代方案并请求验证的场景。用户不盲从"审查报告说不行就不行"，而是基于具体风险点（字段用途差异、静默失败）做最终判断。 | 决策过程较长（4 次迭代），但最终方案与初始方案一致。后续 agent 在类似架构决策中，应允许用户充分讨论替代方案，即使最终回到原方案。装饰器方案的否决理由（字段用途差异、静默失败）具有通用性，后续涉及"自动转换"类方案时可参考。 |
| 2026-07-13 | [自定义字段时间不转换 + 系统级 datetime 字段](.\2026-07-13-custom-records-time-string-not-convert.md) | 用户在处理自定义记录模块的时区迁移问题时，明确区分了"系统时间"和"用户数据"两个概念。对自定义字段中的时间，用户选择原样存储不转换，理由是：(1) 自定义字段只用于显示，不做查询筛选；(2) YYYY-MM-DD HH:MM:SS 格式天然支持字典序排序；(3) 尝试识别并转换会有误转换风险。更关键的是，用户主动发现了一个更深层的设计问题——当前用 `created_at` 做日期筛选语义不正确（创建时间 ≠ 事件时间），并提出了新增必填系统级 datetime 字段的方向。用户在做时间相关决策时，不是简单套用"系统所有时间都转 UTC"的规则，而是根据字段的**职责定位**（系统基础设施 vs 用户数据）来差异化处理。 | 适用于需要区分"系统管理的数据"和"用户输入的数据"的场景。用户的判断模式：先分析字段的职责，再决定处理策略，而非一刀切。当 Agent 能提供合理默认值时，用户倾向必填约束（event_time 必填，无时间时填入当前时间）。 | 区分"系统字段"和"用户字段"是好的抽象，但需要确保边界清晰且在代码中有明确标记。如果未来自定义字段引入 `datetime` 类型并使用它做查询，这个边界会变得模糊，需要重新讨论转换策略。另外，"不转换"策略的前提是"不用于查询"——这是一个容易在需求演变中被忽视的前提，需要在新增查询功能时主动检查。 |
| 2026-07-13 | [日期到 UTC 转换边界与查询参数传递策略](.\2026-07-13-date-to-utc-conversion-boundary.md) | 用户对"就近转换"的位置有明确理解——"组件边界就是转换边界"，坚持"不能让本地时间干扰内部系统，让内部系统保持纯净"。在 AI 主张"API 层转换更便利"时，用户质疑"工程便利性"的实际收益，要求派 subagent 调查实际代码量。调查发现"只有 2 处转换，无工程复用性"后，用户确认采用组件内转换。在混合表决策时，用户提出"如果前端传错误 start_time，后端能否正确解析 date"的技术疑问，在确认可行后才选择"传 date + UTC 范围"方案。 | 适用于用户对"数据纯净性"有清晰原则的场景。用户会主动质疑 AI 提出的"便利性"理由，要求数据验证（实际代码量、实际复用度）而非理论分析。用户对技术方案的选择基于"前提成立"——明确记录决策前提和失效条件。 | 用户对"架构原则 vs 工程便利性"的权衡倾向于架构原则（14 行代码重复可接受）。但这个倾向是基于"复用性不存在"的前提，如果前提失效（转换需求超过 10 个 API），用户可能重新评估。后续 agent 应学习"记录决策前提和失效条件"的模式，而非仅记录最终决策。用户对"过度考虑"的判断依据是风险概率评估（前端格式由浏览器保证 + 格式化函数兜底），这种风险评估方式可参考。 |
| 2026-07-14 | [同步全量同步策略与 LWW 相等跳过](.\2026-07-14-sync-full-sync-strategy.md) | 用户在讨论全量同步方案时，最初提出"都做"（方案一+方案二），但在 AI 评估方案一的修改量、对当前逻辑的损坏、可能引起的 bug 后，用户主动收回，判断"方案二能够完全解决我现在的需求"、"方案一本身就有点过度设计了"。用户的决策依据是"务实优先"——当方案二能完全覆盖当前需求时，不引入方案一的复杂度。用户特别关注方案一在多客户端场景下的"静默数据丢失"风险，认为这种不可恢复的风险比方案二"依赖用户记忆"的风险更严重。在 LWW 相等跳过决策中，用户明确判断"update 相同应该跳过"，理由是无意义的覆盖操作应该避免。 | 适用于用户在"功能完备性 vs 务实简洁"之间的权衡场景。用户会从"当前需求是否完全覆盖"出发评估方案必要性，而非从"未来可能需要"出发。对"静默数据丢失"类风险特别敏感，优先级高于"依赖用户记忆"类风险。 | 用户对"都做"的初始倾向会在 AI 评估具体成本后修正。后续 agent 在用户提出"都做"时，应主动评估每个方案的修改量、对当前逻辑的损坏、可能引起的 bug，帮助用户做务实判断。用户对"过度设计"的判断依据是"当前需求是否完全覆盖"，而非"方案本身是否合理"。 |
| 2026-07-14 | [文件同步冲突处理方案](.\2026-07-14-file-sync-conflict-resolution.md) | 用户在文件同步方案设计中展现了系统性的决策方式：(1) 从不满足于"代码能跑"，会主动排查调用链路是否真正打通；(2) 参考外部成熟方案（思源笔记）但做务实简化——选择 per-file 而非完整 snapshot 树，因为主备模式下完整方案过度设计；(3) 白名单决策遵循"谁写谁同步"的原则——同步白名单 = Agent 工具白名单 + session，每个排除项都有明确的"前提失效时重评估"条件；(4) v2.0 中 MD 冲突从"用户手动处理"转变为"AI 自动合并"——用户识别到 user/ 下 MD 全由 AI 生成，AI 最理解内容语义，果断切换方案；(5) chat_history.json 从"保留在白名单内"变为"明确排除"——因为只有 dreaming task 会改它，而云端不启动 dreaming；(6) 所有决策都基于可校验的前提（主备模式、Agent 白名单不可绕过、云端无前端 API/无 dreaming、user/ MD 由 AI 生成），每个前提失效都有明确的备选触发路径。 | 用户对"决策前提可校验"的要求贯穿本次设计。更关键的是，用户在 v2.0 中展现了"反思与修正"能力——初始方案 MD 冲突由用户手动处理（因为假设 MD 是用户手写），但识别到"user/ MD 全由 AI 生成"后改为 AI 自动合并，并设计了完整的 CONFLICT_RESOLVE 消息类型。用户在做"谁来做这件事"的决策时，会基于"谁最理解这些数据"来判断——数据是 AI 生成的就交给 AI。后续 agent 应先问"这些数据是谁产生的"。此外，在白名单决策中，用户对 chat_history.json 的处理从"保留在目录级白名单里不做逐文件排除"改为"明确排除"，展示了在精确性上的持续完善——当排除理由足够坚固（写入者明确且只有一个）时，会做精确排除。 | 决策转变（手动→AI 自动）依赖前提 7（user/ MD 由 AI 生成）。如果用户开始直接编辑这些文件，AI 合并可能不符合期望，需恢复手动介入。AI 合并失败不做回退（保留本地版本，云端备份在 sync_conflict/），如果合并质量不稳定需评估是否引入确认步骤。chat_history.json 排除依赖前提 8（dreaming task 是唯一写入者+云端不启动 dreaming），如果云端未来启动 dreaming task 或新增其他写入者，需要重新评估。 |

## 决策偏好总结

- 在数据安全与性能之间，优先选择数据安全的方案，即使代价是重复操作
- 评估策略时关注"失败后能否恢复"，而非仅看正常流程的表现
- 对"标准实践"不执着，优先选择最简单可行的方案，但会主动暴露知识盲区并请求确认
- 从实际使用场景出发评估技术方案的必要性，不追求理论上的完备性
- 对不可恢复资源（密钥、token）采取防御性策略，倾向于保留而非删除
- **按字段职责做时间策略分化**：不做"所有时间都转 UTC"的一刀切，而是区分系统级字段（created_at/updated_at/event_time，需要 UTC 统一和查询支持）和用户数据字段（自定义字段，只做展示视为普通字符串）。当 Agent 能提供合理默认值时，倾向必填约束而非可选
- **务实优先于功能完备性**：当当前需求能被简单方案完全覆盖时，不引入复杂方案，即使复杂方案在功能上更完备。判断依据是"当前需求是否完全覆盖"，而非"方案本身是否合理"
- **静默数据丢失 > 依赖用户记忆**：在风险权衡中，不可恢复的静默数据丢失比可缓解的"依赖用户记忆"风险更严重。优先选择不会导致数据丢失的方案，即使代价是用户需要手动操作
- **任务派发基于"谁最理解数据"**：当决定"谁来做合并/处理"时，判断依据不是"谁在看"而是"谁产生了数据"。数据是 AI 生成的就交给 AI，是用户生成的就保留给用户手动介入。这个原则在 v2.0 中驱动了 MD 冲突处理从手动到 AI 自动的转变

## 给后续 agent 的参考

- 设计同步、重试、增量查询相关功能时，必须验证"失败场景下数据是否可恢复"
- 不要仅因为"正常流程性能更好"就选择更细粒度的策略，需先确认失败场景下的数据安全
- 涉及"标准实践 vs 简单方案"时，主动补充技术对比，不要假设用户了解标准实践的优势
- 用户从使用场景倒推技术方案时，帮助标注"使用模式变化后的重新评估条件"
- 涉及不可恢复资源时，默认采取保留策略，而非删除
- **涉及时间处理时，先分析字段的职责定位**——是系统基础设施（created_at 等）还是用户输入数据（自定义字段）。系统级字段做 UTC 转换，用户字段不转换。当 Agent 能提供合理默认值时，推荐必填约束。自定义字段"不转换"的前提是"不用于查询"，新增查询功能时需主动检查此前提是否仍然成立
- **用户提出"都做"时主动评估成本**——当用户初始倾向"都做"多个方案时，应主动评估每个方案的修改量、对当前逻辑的损坏、可能引起的 bug，帮助用户做务实判断。用户会在具体成本评估后收回"都做"的倾向
- **风险权衡中优先避免静默数据丢失**——当方案 A 可能导致静默数据丢失、方案 B 依赖用户记忆但可缓解时，优先选择方案 B。不可恢复的风险比可缓解的风险更严重
- **任务派发先问"数据是谁产生的"**——当设计方案需要"谁来做某件事"（合并、处理、审核）时，先判断数据是谁生成的。AI 生成的数据交给 AI 处理，用户生成的数据保留用户介入。不要默认"用户应该看最终结果"或"AI 可以自动处理一切"。
