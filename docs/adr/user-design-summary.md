# User Design Summary

## 目的

记录用户在重大设计决策中的偏好、判断方式和风险倾向，为后续 agent 自主决策提供参考，也为用户复盘决策方式提供材料。

## 决策行为观察

| 2026-07-09 | [同步原子性策略](.\2026-07-09-sync-atomicity-strategy.md) | 用户在讨论同步错误处理粒度时，主动分析了 row-level best-effort 的致命缺陷——时间戳推进后失败行会永久丢失。用户判断依据是"整体的原子性才对"，认为 last_sync_time 应该代表"所有表已成功同步至此"的语义。 | 适用于涉及数据同步、增量查询、时间戳驱动重试的场景。用户会从"失败后能否恢复"的角度评估策略，而非仅看正常流程。 | 整体原子性会导致成功表重复同步（幂等但浪费资源）。如果同步表数量大幅增加或单次同步耗时长，可能需要重新评估"table-level 容错 + last_sync_time 整体原子"的优化方案。 |
| 2026-07-09 | [密钥存储策略](.\2026-07-09-key-fallback-strategy.md) | 用户在讨论密钥存储方式时，对 .env 和 config.yaml 的区别不确定，主动询问"写入 .env 还是写入文件，和直接写在配置里有什么区别"。用户的决策依据是"简单一点，全部写在一个文件里到时候读取方便"，而非对 12-factor app 实践的认知。 | 适用于用户对"标准实践"不执着、优先选择最简单方案的决策场景。用户会主动暴露自己的知识盲区并请求确认。 | 用户对 .env / 环境变量 / 12-factor app 的认知不深，决策更多基于"直觉上的简单"而非技术对比。后续 agent 在涉及"标准实践 vs 简单方案"时，应主动补充技术对比，而非假设用户了解标准实践的优势。如果未来迁移到容器化部署，需要重新评估。 |
| 2026-07-09 | [冲突解决策略](.\2026-07-09-lww-conflict-resolution.md) | 用户否决 CRDT 和版本号方案的核心依据是"表更改的内容太多"和"使用频率不高，存在较大时间差"。用户从实际使用场景（电脑开机用本地，出门用手机）出发判断冲突概率，而非从理论模型出发。 | 适用于涉及冲突解决、并发控制等理论方案选择时，用户会从实际使用模式出发评估必要性，而非追求理论上的完备性。 | 这种"从使用场景倒推技术方案"的方式在 MVP 阶段是合理的，但如果使用模式变化（如多端同时编辑），需要重新评估。后续 agent 不应假设"用户说不需要就不需要"，应标注触发重新评估的条件。 |

| 2026-07-09 | [cloud_init.yaml 初始化策略](.\2026-07-09-cloud-init-atomic-strategy.md) | 用户在配置初始化策略上选择"验证失败不删除"，核心关注点是"密钥不可恢复"——密钥由本地 keyring 生成，删除文件后如果本地程序已关闭则无法重新获取。 | 适用于涉及不可恢复资源（密钥、token 等）的处理策略。用户对"不可恢复"有清醒认知，倾向于保留而非删除。 | 无重大风险，"保留文件方便重试"是合理的防御性策略。 |
| 2026-07-12 | [迁移到 UTC 时区和 ISO 8601 格式](.\2026-07-12-migrate-to-utc-timezone.md) | 用户主动承认历史技术债——当初选择本地时区是基于"调试方便"、"桌面应用不需要那么复杂"、"对最佳实践不了解"等原因。在了解业界最佳实践（Laravel/ActivityWatch 等都强制 UTC）和现有问题（时区不一致导致数据同步失败）后，选择迁移到 UTC。用户对"即使桌面应用也需要 UTC"的认知转变来自具体案例（ActivityWatch）而非理论说教。 | 适用于用户对历史决策有清醒认知、愿意承认知识局限、并在有充分证据时修正方向的场景。用户的决策转变依赖于"具体案例 + 现有问题"的双重驱动，而非单纯的理论最佳实践。 | 迁移成本大（100+ 处代码 + 历史数据），但用户已接受。需注意用户对"最佳实践"的认可是基于"已出现问题 + 同类项目案例"，而非预防性采纳。后续 agent 在推荐最佳实践时，应结合"当前痛点 + 具体案例"，而非仅引用官方文档。 |
| 2026-07-12 | [时间转换职责分层架构](.\2026-07-12-time-conversion-layering.md) | 用户在决策过程中经历了明显的动摇：先是质疑"一层层过滤"是否合理，一度想改 Repository 层增加 `return_local_time` 参数（因为"修改点较多且容易出错"），又主动提出装饰器方案（想减少重复代码），并要求"派出 agent 审查是否合理"。审查报告指出装饰器的静默失败、字段用途差异等风险后，用户确认回到原方案。用户在动摇时会主动寻求外部审查，而非固执己见。 | 适用于用户对架构方案有动摇时，会主动提出替代方案并请求验证的场景。用户不盲从"审查报告说不行就不行"，而是基于具体风险点（字段用途差异、静默失败）做最终判断。 | 决策过程较长（4 次迭代），但最终方案与初始方案一致。后续 agent 在类似架构决策中，应允许用户充分讨论替代方案，即使最终回到原方案。装饰器方案的否决理由（字段用途差异、静默失败）具有通用性，后续涉及"自动转换"类方案时可参考。 |
| 2026-07-13 | [日期到 UTC 转换边界与查询参数传递策略](.\2026-07-13-date-to-utc-conversion-boundary.md) | 用户对"就近转换"的位置有明确理解——"组件边界就是转换边界"，坚持"不能让本地时间干扰内部系统，让内部系统保持纯净"。在 AI 主张"API 层转换更便利"时，用户质疑"工程便利性"的实际收益，要求派 subagent 调查实际代码量。调查发现"只有 2 处转换，无工程复用性"后，用户确认采用组件内转换。在混合表决策时，用户提出"如果前端传错误 start_time，后端能否正确解析 date"的技术疑问，在确认可行后才选择"传 date + UTC 范围"方案。 | 适用于用户对"数据纯净性"有清晰原则的场景。用户会主动质疑 AI 提出的"便利性"理由，要求数据验证（实际代码量、实际复用度）而非理论分析。用户对技术方案的选择基于"前提成立"——明确记录决策前提和失效条件。 | 用户对"架构原则 vs 工程便利性"的权衡倾向于架构原则（14 行代码重复可接受）。但这个倾向是基于"复用性不存在"的前提，如果前提失效（转换需求超过 10 个 API），用户可能重新评估。后续 agent 应学习"记录决策前提和失效条件"的模式，而非仅记录最终决策。用户对"过度考虑"的判断依据是风险概率评估（前端格式由浏览器保证 + 格式化函数兜底），这种风险评估方式可参考。 |

## 决策偏好总结

- 在数据安全与性能之间，优先选择数据安全的方案，即使代价是重复操作
- 评估策略时关注"失败后能否恢复"，而非仅看正常流程的表现
- 对"标准实践"不执着，优先选择最简单可行的方案，但会主动暴露知识盲区并请求确认
- 从实际使用场景出发评估技术方案的必要性，不追求理论上的完备性
- 对不可恢复资源（密钥、token）采取防御性策略，倾向于保留而非删除

## 给后续 agent 的参考

- 设计同步、重试、增量查询相关功能时，必须验证"失败场景下数据是否可恢复"
- 不要仅因为"正常流程性能更好"就选择更细粒度的策略，需先确认失败场景下的数据安全
- 涉及"标准实践 vs 简单方案"时，主动补充技术对比，不要假设用户了解标准实践的优势
- 用户从使用场景倒推技术方案时，帮助标注"使用模式变化后的重新评估条件"
- 涉及不可恢复资源时，默认采取保留策略，而非删除
