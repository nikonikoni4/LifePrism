# 通信架构：REST 轮询 vs WebSocket vs 云端推送

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿 |

## 问题界定

### 问题简述

LifeWatch-AI 的本地（Windows）和云端（Linux）之间需要建立数据同步通道。需要决定通信方向（谁主动发起）、通信协议和同步频率。

### 讨论范围

- 通信方向：本地主动 vs 云端主动 vs 双向
- 通信协议：HTTP REST vs WebSocket
- 同步频率：实时 vs 定时

### 非讨论范围

- 冲突解决策略（已在 `2026-07-09-lww-conflict-resolution.md` 中决定）
- 同步原子性（已在 `2026-07-09-sync-atomicity-strategy.md` 中决定）
- HTTPS 证书管理（属于 Issue #11 运维范畴）

### 模糊信息的明确定义

- `NAT 穿透`：家庭网络通常在 NAT 后面，外部无法直接访问家庭网络内的设备。需要端口转发或 NAT 穿透技术才能从外部访问本地服务。
- `轮询 (Polling)`：客户端定时向服务器发起请求获取更新，而非服务器主动推送。

### 问题深度

涉及同步系统的通信架构，选择影响部署方式、网络配置和运维复杂度。后续切换通信协议成本高（需重写客户端和服务端通信层）。

## 现状

- 本地 Windows 运行在家庭网络中，位于 NAT 后面
- 云端 Linux 运行在公网服务器上，有固定 IP 和域名
- 用户使用模式：电脑开机时用本地，出门或关机时用手机访问云端
- 同步频率低，本地和云端之间通常存在较大的时间差

## 可选方案

### 方案 A：HTTP REST + 本地主动轮询（已实现）

Windows 本地定时向云端发起 HTTP REST 请求，拉取和推送增量数据。

**优势**

- 简单可靠，不需要 WebSocket 长连接
- 本地主动发起，避免 NAT 穿透问题
- 云端被动响应，不需要知道本地 IP
- 10 分钟间隔已足够（不需要实时同步）
- HTTP/HTTPS 生态成熟，调试方便

**劣势**

- 非实时同步，最多有 10 分钟延迟
- 轮询有空转开销（无变更时仍发请求）

### 方案 B：WebSocket 长连接

建立 WebSocket 双向通道，云端有变更时主动推送。

**优势**

- 实时同步，延迟低
- 无轮询空转

**劣势**

- 需要维护长连接，增加复杂度
- 连接断开后需要重连逻辑
- 云端需要知道本地地址或本地需要保持连接，NAT 超时可能导致断连
- 过度设计：同步频率低，不需要实时性

### 方案 C：云端主动推送

云端检测到变更后，主动向本地推送数据。

**优势**

- 本地无需主动发起

**劣势**

- 本地在 NAT 后面，云端无法直接访问
- 需要端口转发或 NAT 穿透技术
- 家庭 IP 可能变化（动态 IP）
- 运维复杂度高

## 最终决策

选择 **方案 A：HTTP REST + 本地主动轮询**。

## 决策原因

- 原因 1：使用模式决定无需实时同步。用户使用模式是"电脑开机时用本地，出门或关机时用手机"，同步频率低、时间差大。10 分钟的轮询间隔已经足够，不需要 WebSocket 的实时性。
- 原因 2：NAT 穿透问题。本地 Windows 在家庭网络 NAT 后面，云端无法直接访问。本地主动发起 HTTP 请求是最简单的方案，无需端口转发或 NAT 穿透。
- 原因 3：简单可靠。HTTP REST 是最成熟的通信方式，调试方便（curl 即可测试），不需要维护长连接和重连逻辑。WebSocket 和云端推送方案增加的复杂度在当前使用模式下没有收益。

## 后续影响

- 同步最多有 10 分钟延迟，用户需要知晓这一限制
- 轮询间隔（600 秒）可在配置中调整
- 如果未来需要实时同步（如多端同时编辑），需要重新评估 WebSocket 方案
- 云端需要配置 HTTPS（Let's Encrypt）和 API Key 认证，确保 REST API 安全
