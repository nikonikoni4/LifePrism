# 同步全量同步策略与 LWW 相等跳过

## 版本

| 版本 | 更新内容 |
| ---- | -------- |
| 1.0 | 创建文档初稿，包含两个关联决策：全量同步方案选择 + LWW 相等跳过 |

## 问题界定

### 问题简述

同步系统完全依赖客户端 `last_sync_time` 判断增量范围。在以下场景下，当前逻辑无法自动触发全量同步：

1. **换服务器**：新服务器的数据库为空，但客户端仍按本地 `last_sync_time` 做增量查询，导致云端 Pull 返回空数据、Push 也只推送 `updated_at > last_sync_time` 的少量记录，云端数据不完整。
2. **云端数据库损坏后重建**：同上，云端数据被清空后无法通过增量同步恢复。
3. **本地数据库重置**：本地无数据但 `last_sync_time` 仍为旧值，Pull 会拉取大量数据但 Push 推送不出任何数据（逻辑上无问题，但语义混乱）。

同时，在排查同步问题时发现 LWW 冲突解决逻辑存在一个边界问题：当本地和云端记录的 `updated_at` 完全相等时，当前逻辑会按"远程覆盖本地"（Pull 端）或"本地覆盖云端"（Push 端）处理，这种无意义的覆盖操作应改为跳过。

### 讨论范围

- 同步系统全量同步的触发机制
- LWW 冲突解决中"时间相等"的处理策略
- 云端是否需要维护同步状态

### 非讨论范围

- 同步频率调整（已在 rest-polling-communication ADR 中决定为 10 分钟）
- 同步原子性策略（已在 sync-atomicity-strategy ADR 中决定为全局原子性）
- 多客户端并发同步的支持（当前不存在该场景）

### 问题深度

全量同步策略涉及同步架构的长期演进方向——是否引入云端状态。LWW 相等跳过是冲突解决策略的细节优化，属于浅层方案选择。

## 现状

### 同步架构现状

- **通信方式**：HTTP REST + 本地主动轮询（10 分钟）
- **冲突解决**：LWW（Last-Write-Wins），比较 `updated_at` 时间戳
- **`last_sync_time` 归属**：存储在客户端 `localData/config/config.yaml`，每次 Pull 通过 POST BODY 发给云端，云端用完即弃（无状态）
- **增量查询**：`SELECT * FROM {table} WHERE updated_at > ?`，`?` 为 `last_sync_time`
- **使用模式**：当前只有电脑端一个客户端，无手机端

### 已知事实

1. 所有 30 张静态同步表 + 动态自定义记录表都配置了 `"update_at": True`，都有物理 `updated_at` 列
2. 清空 `last_sync_time`（设为空字符串）后：
   - Pull 时云端执行 `WHERE updated_at > ""` 返回所有记录
   - Push 时本地执行 `WHERE updated_at > ""` 返回所有记录
   - 即"清空 `last_sync_time`"天然等价于"全量同步"
3. 前端已有"手动同步"按钮，可立即触发 `sync_once()`

### 代码注释的过时问题

`sync_client.py` 第 298-303 行的注释声称"部分表无物理 updated_at 列"，但实际上所有表都配置了 `update_at: True`。该注释是过时的——可能是某次给所有表补 `update_at: True` 之后忘了更新注释。本次决策不涉及修改该注释（属于代码清理范畴），但记录此事实以避免后续误导。

## 决策前提

- **前提 1**：当前使用模式为单客户端（仅电脑端），无手机端
- **前提 2**：方案二（重置同步进度按钮）能完全覆盖当前的全量同步需求（换服务器、云端 DB 重置、本地 DB 重置）
- **前提 3**：方案一会引入云端状态管理复杂度，且在多客户端场景下需要重构引入 client_id
- **前提 4**：LWW 中 `updated_at` 相等属于"数据完全一致"的幂等场景，跳过比覆盖更合理

## 可选方案

### 方案 A：云端维护同步时间（方案一）

云端新增一张 `sync_state` 表存储 `last_sync_time`。Pull API 不再用请求参数，改读 `sync_state`，并在响应中返回使用的时间；Push API 成功后更新 `sync_state`。客户端 Pull 后保存云端返回的时间，传给 Push 使用。

**优势**

- 换服务器时自动触发全量同步（新服务器 `sync_state` 为空）
- 云端 DB 重置后自动全量同步（`sync_state` 表清空）
- 客户端本地无需维护 `last_sync_time`

**劣势**

- 改动量大：云端 4 个端点 + 客户端 4 个方法都要改
- 引入云端状态管理复杂度（新增表、读写逻辑、状态更新时机）
- **多客户端场景下的静默数据丢失风险**：全局 `last_sync_time` 会导致轮流同步的客户端漏掉数据（详见"决策原因"）
- 未来引入手机端时需要重构为 `client_id` 机制

### 方案 B：重置同步进度按钮（方案二）

在前端设置界面云端同步区域增加"重置同步进度"按钮，点击后清空本地 `last_sync_time`。现有"手动同步"按钮重命名为"手动同步（增量）"。用户重置后点击"手动同步（增量）"即等价于全量同步。

**优势**

- 改动量小：仅前端加一个按钮 + 调用 settings_manager 清空字段
- 完全解决当前需求（换服务器、云端 DB 重置、本地 DB 重置都可手动触发全量同步）
- 不引入云端状态，保持云端无状态设计
- 天然支持多客户端（每个客户端各自维护 `last_sync_time`）
- 测试便利：用户明确提到"全量同步比较好测试"

**劣势**

- 依赖用户记忆：换服务器时用户需记得点"重置"按钮，否则会按错误的 `last_sync_time` 增量同步
- 需要二次确认弹窗（避免误操作导致全量同步耗时）

## 最终决策

### 决策 1：全量同步策略

当前成立的前提：单客户端使用模式 + 方案二能完全覆盖当前需求 + 方案一引入不必要的复杂度。

因此选择 **方案 B（重置同步进度按钮）**。

前提失效时的切换路径：当多客户端场景出现时（如引入手机端），重新评估是否引入方案一或 `client_id` 机制。

### 决策 2：LWW 相等跳过

当前成立的前提：`updated_at` 相等表示数据完全一致，覆盖操作是幂等的无意义写入。

因此选择 **`updated_at` 相等时跳过**：

- Push 端（`sync_repository.py`）：`existing_updated_at > incoming_updated_at` 改为 `existing_updated_at >= incoming_updated_at`，即云端已有记录的 `updated_at` 大于或等于传入记录时都跳过
- Pull 端（`sync_client.py`）：新增 `str(remote_updated_at) == str(local_updated_at)` 分支，跳过不写入

## 决策原因

### 决策 1 的原因

- **方案二是务实的最小可行方案**：用户明确判断"方案二能够完全解决我现在的需求"，方案一属于过度设计
- **方案一的多客户端风险是静默数据丢失**：即使当前是单客户端，方案一的全局 `last_sync_time` 在多客户端轮流同步时会导致数据永久丢失。具体场景：客户端 A 同步后云端 `last_sync_time` 推进到 T2，客户端 B 在 T3（T2 < T3 < T5）创建的记录，在 B 同步时云端已推进到 T5，`WHERE updated_at > T5` 查不到 T3 的记录，数据永久丢失。这种丢失是静默的、不可恢复的
- **方案二天然支持多客户端**：每个客户端各自维护 `last_sync_time`，互不干扰
- **方案二的"依赖用户记忆"风险可通过 UI 提示缓解**：可后续考虑检测到 `remote_url` 变化时弹窗提示"是否重置同步进度"（本次决策不强制实现）
- **方案一在云端 DB 重置场景反而不如方案二直接**：用户明确指出"如果引入云端时间，想把云端数据全部重置是做不到的"——方案一下云端 `sync_state` 表本身也是状态，重置时需要额外清理

### 决策 2 的原因

- **相等跳过是 LWW 的合理细化**：`updated_at` 相等意味着两条记录的最后修改时间完全一致，在 UTC 统一时间戳的前提下，这等价于数据完全一致，无需覆盖
- **减少无意义的写入操作**：覆盖相等记录会产生无意义的 `INSERT OR REPLACE`，增加数据库 IO 和 WAL 日志
- **保持 Pull/Push 双端行为对称**：Push 端跳过相等记录，Pull 端也应跳过，避免单向覆盖
