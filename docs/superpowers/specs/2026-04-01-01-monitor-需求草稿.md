# Monitor 模块需求草稿 (v1.0)

## 1. 产品概述 (Why)

Monitor 模块是 LifeWatch-AI 的数据采集层，旨在通过多进程架构替代外部的 ActivityWatch 插件（如 aw-watcher-window），实现更原生、更可控的电脑活动监控。它不仅负责记录窗口活动，还需为未来的键盘频率监控和屏幕截图功能预留扩展空间。

## 2. 业务逻辑 (What & When)

### 2.1 阶段 1：窗口监控 (移植 aw-watcher-window)
- **核心功能**：实时捕获当前活动窗口的 `app`（程序名）和 `title`（窗口标题）。
- **上报频率**：
    - 默认采用「心跳」机制（Heartbeat）。
    - 采样频率：每 1 秒采样一次。
    - 聚合策略：如果当前窗口未变化，则合并为一个持续的事件；如果发生变化，则结束当前事件并开始新事件。
    - 最小切片：记录应保持与 ActivityWatch 的 `aw-watcher-window` 格式兼容，支持 `duration` 字段。
- **活跃判定**：
    - 需捕获系统「空闲（Idle）」状态。若用户超过 X 秒（默认 180s）无操作，应停止记录或记录为 Idle 状态。

### 2.2 阶段 2：键盘监控 (占位)
- **核心功能**：统计每分钟按键次数（KPM），不记录具体键值（保护隐私）。

### 2.3 阶段 3：屏幕截图 (占位)
- **核心功能**：定时（如每 5 分钟）或触发式拍摄当前屏幕缩略图，用于辅助分类校验。

## 3. 数据设计 (Structure & Constraints)

### 3.1 存储集成
- **数据流向**：Monitor 进程 -> `lifewatch_ai.db` (Table: `user_app_behavior_log`)。
- **兼容性**：数据格式必须与 `USER_APP_BEHAVIOR_LOG_CONFIG` 完全一致。
- **字段映射**：
    - `id`: 生成 UUID 或使用与 AW 兼容的标识符。
    - `start_time` / `end_time`: ISO 8601 格式字符串（本地时间）。
    - `app`: 执行文件名（如 `msedge.exe`）。
    - `title`: 窗口标题。
    - `duration`: 持续秒数。

### 3.2 配置集成
- 从 `settings_manager` 读取配置：
    - `monitor_enabled`: 是否开启监控。
    - `sampling_interval`: 采样间隔。
    - `idle_threshold`: 空闲判定阈值。

## 4. 后端架构 (How)

### 4.1 多进程管理
- **运行模式**：独立于 FastAPI 主进程。由 `main.py` 启动或通过独立入口启动。
- **生命周期**：
    - **启动**：后端服务启动时自动拉起 Monitor 进程。
    - **监控**：主进程需监控 Monitor 进程状态，崩溃后自动重启（指数退避策略）。
    - **停止**：主进程退出时发送信号（SIGTERM）优雅关闭 Monitor 进程，确保缓冲区数据写入 DB。
- **日志收集**：Monitor 进程的日志应通过管道重定向至主进程日志系统，或独立写入 `debug_logs/monitor.log`。

### 4.2 窗口捕获实现 (Windows)
- 使用 `pygetwindow` 或直接调用 `Win32 API` (`GetForegroundWindow`, `GetWindowText`, `GetWindowThreadProcessId`)。

## 5. 集成风险与难点
- **进程间通信 (IPC)**：虽然 Monitor 直接写 DB，但如果主进程需要实时状态（如当前是否正在监控），可能需要简单的 IPC 或文件锁。
- **性能开销**：高频采样对 CPU 的影响需控制在 1% 以下。
- **权限问题**：捕获某些窗口标题可能需要管理员权限。

## 6. 验收标准
- [ ] Monitor 进程能随主进程启动并成功在 `user_app_behavior_log` 产生数据。
- [ ] 产生的数据格式能被 `data_clean.py` 的现有逻辑无缝解析。
- [ ] 在 `settings.yaml` 中关闭监控后，Monitor 进程能正常退出。
- [ ] 连续运行 24 小时，无内存泄漏且进程存活。

## 7. 开放性提问与待定方案

### 7.1 数据冲突处理
- 如果用户同时运行原版 ActivityWatch 且开启了 Monitor，如何避免 `user_app_behavior_log` 中的数据重复或冲突？
- **建议方案**：Monitor 记录时可以带上 `source` 标识（如 `monitor_internal` vs `activitywatch`），或在 `settings` 中强制二选一。

### 7.2 窗口捕获库选择
- 是使用成熟的第三方库（如 `pygetwindow`）还是直接调用原生 `Win32 API`？
- **决策因素**：原生 API 虽然复杂，但可以获得更细粒度的信息（如窗口类名、所属进程路径），且不依赖额外库。

### 7.3 多进程通信 (IPC)
- 是否需要向主进程同步「当前正在运行的程序」？这在前端 Dashboard 实时显示当前状态时非常有用。
- **建议方案**：使用内存映射文件（Shared Memory）或简单的本地 Socket 广播实时状态。

### 7.4 阶段 2/3 的资源隔离
- 键盘监控和截图功能是否应运行在同一个 Monitor 进程中，还是拆分为多个子进程？
- **建议方案**：Monitor 作为一个管理器进程，通过子线程或子进程分别拉起不同的 Observer（Window, Keyboard, Screenshot），增强容错性。
