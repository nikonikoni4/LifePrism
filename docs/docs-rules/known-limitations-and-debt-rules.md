# Known-limitations 与 Technical-debt 区分规则

## 1. 三类文档的核心定义

### 1.1 known-limitations（已知限制）

> **"当前系统就是这样运作的，这是设计选择或现实约束，不是 bug"**

- **消费者**：AI + 开发者
- **回答的问题**：为什么是这样？
- **是否必须修复**：**不一定**，很多是有意识地接受现状
- **时间属性**：长期存在，提供项目上下文
- **关键标志**：依赖某个**前提**才成立（如"用户所在地 = 系统时区"、"本机使用时云端不产生数据"）
- **用途**：AI 读了之后知道"这里不能动 / 这里这样是有原因的"，避免"好心办坏事"去改一个看起来不合理但其实是有意为之的设计
- **典型状态**：`acknowledged` 长期挂着

### 1.2 technical-debt（技术债）

> **"这里代码不够好，未来应该改，但当前能跑"**

- **消费者**：开发者 + AI
- **回答的问题**：怎么改？
- **是否必须修复**：**必须**，只是时间问题
- **时间属性**：中期，待还债
- **关键标志**：有**明确的代码位置** + **明确的优化方向**（哪怕只是粗略方向）
- **用途**：AI/开发者在改相关代码时知道"这里有债，要小心，最好顺便还了"
- **典型内容**：重构未完成、为快速上线留下的潜在问题、模块放错位置

### 1.3 progress（待办/调研）

> **"已经识别出问题/机会，但连方案都还没定"**

- **消费者**：开发者自己
- **回答的问题**：接下来做什么？
- **是否必须修复**：待定（连方案都没定）
- **时间属性**：短期，过程性，方案定下就归档
- **关键标志**：含**开放性问题**（"选 SQLite 还是 PostgreSQL？""阈值定多少？"）
- **用途**：自己跟踪思路，不提供长期项目上下文

## 2. 判定决策树

```
1. 方案是否已经确定？
   ├─ 否（还在调研/讨论） → progress
   └─ 是（已决定修复方向）
       │
2. 修复动机是什么？
   ├─ "代码质量/设计错位"（模块放错地方、硬编码、冗余）
   │   → technical-debt
   │
   └─ "突破现实约束/前提"（架构前提、安全前提、时区前提）
       → known-limitations
       │
3. 同一个事实是否同时具有两种属性？
   ├─ 是 → 两边都写，但视角不同（见第 3 节）
   └─ 否 → 单一归属
```

## 3. 重叠内容的处理：一个事实，两个视角

**不要纠结二选一**。当一个事实既是"约束"又是"债务"时，两边都写，但侧重点严格区分：

| 文档 | 写什么 | 不写什么 |
|------|--------|----------|
| known-limitations | **事实 + 前提 + 为什么接受**（AI 上下文） | 具体修复方案 |
| technical-debt | **代码位置 + 修复方案 + 影响范围**（开发指引） | 重复解释"为什么这样" |

两边用相对路径或 `[[]]` 互相引用即可。

### 3.1 范例：behavior.md 增长问题

- `known-limitations/behavior-md-growth-and-sync-impact.md`：讲"behavior.md 持续增长是已知问题，当前 ~300KB 可接受，触发条件是 1MB+"
- `technical-debt/behavior-md-large-file-one-way-sync.md`：讲"方案 A 单向白名单 + 方案 B 按月拆分，推荐顺序 A→B"

## 4. 与 ADR 的边界

known-limitations 与 ADR 存在重合，但职责不同：

| 维度 | ADR | known-limitations |
|------|-----|-------------------|
| 关注点 | **为什么做出这个决策**（决策时刻的上下文 + 备选方案） | **当前系统受什么约束**（运行时的限制 + 触发条件） |
| 时间属性 | 历史性，决策定型后不再改 | 现状性，可能随前提变化而消除 |
| 写作视角 | 决策者视角（权衡） | 运行视角（约束 + 影响） |

**重合时的处理**：ADR 链接到 known-limitations 作为"决策带来的限制"，known-limitations 引用 ADR 作为"为什么这样"的依据。例如 UTC 时区迁移 ADR + 时区显示解耦限制就是这种关系。

## 5. progress 的生命周期

progress 是过程性文档，**方案一旦确定必须迁移**：

| 方案结论 | 迁移动作 |
|----------|----------|
| 修复方向明确 | 拆出 `technical-debt` 文档 + `plans/active/` 任务，原 progress 文档归档或删除 |
| 仅接受现状 | 迁移到 `known-limitations`，原 progress 文档归档或删除 |
| 不再追踪 | 直接归档或删除 |

**禁止**：让 progress 长期堆积"已过期讨论"。progress 不提供长期项目上下文，留着会污染检索。

## 6. 写作模板

### 6.1 known-limitations 文档模板

参照 `docs/known-limitations/index.md` 中的"文档格式"章节，必备字段：
- 问题描述
- 影响范围 + 严重程度
- 当前假设（系统依赖的脆弱前提）
- 触发条件
- 临时方案或计划改进
- 相关文档（ADR、调查报告等）

### 6.2 technical-debt 文档模板

参照现有 `docs/technical-debt/*.md` 的结构，必备字段：
- 问题描述（含明确代码位置）
- 当前影响（token/性能/维护成本等量化数据）
- 优化方案（可多个，标注推荐顺序）
- 相关代码文件
- 相关文档（ADR、known-limitations 等）

## 7. 归档规则

- `known-limitations` 状态变为 `resolved` → 归档到 history（或直接删除并更新 index）
- `technical-debt` 修复完成 → 移到 `plans/completed/` 关联的任务下，或在文档顶部标注 `状态: resolved` 并归档
- `progress` 方案确定 → 按第 5 节迁移后删除原文件
