# 任务池视图

> 单栏模式下的独立视图，展示所有未分配日期的任务，支持从计划书同步任务

---

### 交互规则

1. **同步**：点击 [同步] → 从关联计划书解析任务 → 更新任务池
2. **筛选**：按目标、计划书筛选任务
3. **分配日期**：点击 [分配日期] → 弹出日期选择器 → 状态变为 `scheduled`
4. **完成任务**：勾选任务 → 状态变为 `completed` → 回写计划书 MD
5. **拖拽**：支持拖拽到日历视图分配日期

### 视觉规范

## 3. MD 格式规范

### 3.1 锚点格式

```markdown
- [ ] 任务内容 <!-- lp:t-abc123 -->
```

- `lp:` = LifePrism 前缀
- `t-` = task 类型
- `abc123` = uuid 前 8 位

### 3.2 计划书结构示例

```markdown
# React 学习计划

## 学习目标

掌握 React 核心概念...

## 任务清单

<!-- lp:todoblock -->
- [ ] 学习 React 基础 <!-- lp:t-abc12345 -->
	- [ ] 理解 JSX 语法 <!-- lp:t-def67890 -->
	- [x] 学习组件概念 <!-- lp:t-ghi11111 -->
- [ ] 学习 Hooks <!-- lp:t-jkl22222 -->
	- [ ] 理解 useState <!-- lp:t-mno33333 -->
	- [ ] 理解 useEffect <!-- lp:t-pqr44444 -->
<!-- /lp:todoblock -->

## 参考资料

- React 官方文档
- ...

---

## 任务总览
<!-- lp:system-section -->
> 此区域由系统自动生成，手动修改将在下次同步时被覆盖

- [ ] 学习 React 基础
	- [ ] 理解 JSX 语法
	- [x] 学习组件概念
- [ ] 学习 Hooks
	- [ ] 理解 useState
	- [ ] 理解 useEffect
```

### 3.3 解析规则

1. **任务块识别**：只解析 `<!-- lp:todoblock -->` 和 `<!-- /lp:todoblock -->` 之间的内容
2. **系统区域**：`<!-- lp:system-section -->` 之后的内容（同步时覆盖）
3. **任务识别**：在任务块内匹配 `- [ ] xxx` 或 `- [x] xxx` 格式
4. **锚点提取**：匹配 `<!-- lp:t-xxx -->` 获取 `source_anchor_id`
5. **层级识别**：通过 Tab 缩进判断父子关系（见 3.4）

### 3.4 缩进与层级规则

**任务块识别**：

任务必须在专用任务块内才会被解析同步：

```markdown
<!-- lp:todoblock -->
- [ ] 任务 A
	- [ ] 子任务 A1
	- [ ] 子任务 A2
- [ ] 任务 B
<!-- /lp:todoblock -->
```

- 开始标记：`<!-- lp:todoblock -->`
- 结束标记：`<!-- /lp:todoblock -->`
- 块外的 `- [ ]` 不会被解析为任务

**缩进规则**（已确认）：

- 缩进单位：**Tab**（1 Tab = 1 级）
- MD 编辑器限制：一次只能缩进一个 Tab
- 不支持空格缩进，只有 Tab 生效

**层级判断算法**：

1. 统计每行开头的 Tab 数量
2. 0 个 Tab = 根任务（level 0）
3. 1 个 Tab = 一级子任务（parent = 最近的 level 0 任务）
4. N 个 Tab = N 级子任务（parent = 最近的 level N-1 任务）

**示例**：

```markdown
<!-- lp:todoblock -->
- [ ] 任务 A              ← 0 Tab, level 0, parent = NULL
	- [ ] 子任务 A1       ← 1 Tab, level 1, parent = 任务 A
	- [ ] 子任务 A2       ← 1 Tab, level 1, parent = 任务 A
		- [ ] 孙任务 A2a  ← 2 Tab, level 2, parent = 子任务 A2
- [ ] 任务 B              ← 0 Tab, level 0, parent = NULL
<!-- /lp:todoblock -->
```
```

### 4.2 同步计划书任务

```
POST /api/v2/taskpool/sync
```

**请求**：

```json
{
  "plan_doc_id": "plandoc-xxx"
}
```

**处理流程**：

```
1. 读取 plan_doc 的 MD 内容
2. 查找 <!-- lp:todoblock --> 和 <!-- /lp:todoblock --> 之间的内容
3. 提取所有 - [ ] 和 - [x] 任务，解析出：
   - content（任务内容）
   - source_anchor_id（锚点 ID，可能为空）
   - parent_anchor_id（父任务锚点，通过缩进判断）
   - md_checked（MD 中是否为 [x]，临时变量，用于判断是否同步完成状态）

4. 对于每个任务，按以下规则处理：
   │
   ├─ 情况 A：有锚点 + 有内容 + 有 [ ]
   │   └─ 匹配已有 todo → 全量更新字段
   │
   ├─ 情况 B：无锚点 + 有内容 + 有 [ ]
   │   └─ 生成 t-{uuid[:8]} → 创建 todo → 写回锚点到 MD
   │
   ├─ 情况 C：有锚点 + 无 [ ]（用户删除了勾选框但保留了锚点）
   │   └─ 清理该行的锚点注释，不更新 todo
   │
   └─ 情况 D：有锚点 + 有 [ ] + 无内容（空任务）
       └─ 忽略，不更新 todo（视为错误格式）

5. 处理系统展示区：
   ├─ 如果 <!-- lp:system-section --> 不存在 → 在文件末尾添加
   └─ 重新生成系统展示区内容

6. 保存 plan_doc
```

**同步字段说明**：

采用**全量更新**策略，每次同步都将 MD 解析结果视为完整数据源，更新以下字段：

| 字段 | 来源 | 说明 |
|:---|:---|:---|
| `content` | MD 任务文本 | 任务内容（去除锚点注释后） |
| `parent_id` | MD 缩进层级 | 通过 `parent_anchor_id` → 查找 `todo.id` |
| `pool_order_index` | MD 出现顺序 | 按解析顺序递增 |
| `state` | MD 勾选状态 | **单向同步**：`[x]` → `completed`，见下方规则 |

**`state` 同步规则（双向但单向生效）**：

| MD 状态 | 当前 `state` | 同步后 `state` | 说明 |
|:---|:---|:---|:---|
| `[x]` | `pool` | `completed` | MD 勾选 → 标记完成 |
| `[x]` | `scheduled` | `completed` | MD 勾选 → 标记完成 |
| `[x]` | `completed` | `completed` | 无变化 |
| `[ ]` | `pool` | `pool` | 无变化 |
| `[ ]` | `scheduled` | `scheduled` | 无变化 |
| `[ ]` | `completed` | `completed` | **不允许取消完成** |

> 用户可以在 MD 中勾选 `[x]` 来完成任务，但不能通过改回 `[ ]` 来取消完成状态。

**不更新的字段**（保留用户在系统中的设置）：

| 字段 | 原因 |
|:---|:---|
| `date` | 用户在日历视图分配的日期 |
| `color` | 用户设置的颜色 |
| `order_index` | 日历视图中的排序 |
| `expected_finished_at` | 用户设置的预计完成日期 |
| `actual_finished_at` | 系统记录的实际完成日期 |
| `link_to_goal_id` | 继承自 plan_doc 的 goal_id，创建时设置 |
| `plan_doc_id` | 创建时设置，不变 |
| `source_anchor_id` | 创建时设置，不变 |

**缩进变化处理**：

全量更新 `parent_id` 可以自动处理以下场景：

1. **子任务变为根任务**：用户减少缩进 → `parent_id` 更新为 `NULL`
2. **根任务变为子任务**：用户增加缩进 → `parent_id` 更新为新父任务 ID
3. **父任务被删除**：子任务的 `parent_id` 指向的锚点不存在 → `parent_id` 设为 `NULL`
4. **任务层级调整**：任意缩进变化都会正确反映

**关于任务删除**：

- **MD 没有删除 todo 的权利**
- 用户在 MD 中删除任务行（包括 `[ ]` 和锚点），该 todo 仍保留在数据库中
- 被删除的任务：
  - 不再在用户区域显示完成状态
  - 会在系统展示区正常显示
  - `parent_id` 保持不变（不会因为 MD 中不存在而清空）

**响应**：

```json
{
  "created": 3,
  "updated": 2,
  "cleaned": 1,
  "total": 10
}
```

### 4.3 更新任务

```
PUT /api/v2/todos/{id}
```

**请求**：

```json
{
  "state": "completed",
  "date": "2026-02-05"
}
```

**回写 MD 的前置条件**：

当 `state` 变为 `completed` 时，需要同时满足以下条件才回写：

1. 任务有 `source_anchor_id`
2. 任务有 `plan_doc_id`
3. MD 文件中存在对应的锚点 `<!-- lp:{source_anchor_id} -->`
4. 锚点所在行存在 `- [ ]` 格式

**回写流程**：

```
1. 检查前置条件
2. 如果条件满足：
   ├─ 找到 <!-- lp:{source_anchor_id} --> 所在行
   ├─ 将 - [ ] 改为 - [x]
   ├─ 更新系统展示区
   └─ 保存 plan_doc
3. 如果条件不满足：
   └─ 仅更新 todo 表状态，记录警告日志
```

**异常处理**：

| 异常情况 | 处理方式 |
|:---|:---|
| plan_doc 不存在 | 仅更新 todo 状态，记录警告日志 |
| MD 文件不存在 | 仅更新 todo 状态，记录警告日志 |
| 锚点未找到 | 仅更新 todo 状态，记录警告日志 |
| 锚点存在但无 `[ ]` | 仅更新 todo 状态，记录警告日志 |
| 文件写入失败 | 返回 500 错误，回滚 todo 状态变更 |

### 4.4 重新生成系统展示区

```
POST /api/v2/taskpool/regenerate-summary
```

**请求**：

```json
{
  "plan_doc_id": "plandoc-xxx"
}
```

**处理**：

1. 获取该 plan_doc 关联的所有 todo（树形结构）
2. 生成 MD 格式任务列表（不含锚点注释）
3. 如果 `<!-- lp:system-section -->` 不存在：
   - 在文件末尾添加 `---` 分隔线
   - 添加 `## 任务总览` 标题
   - 添加 `<!-- lp:system-section -->` 标记
4. 替换 `<!-- lp:system-section -->` 之后的内容
5. 保存 plan_doc

### 4.5 并发控制

**前端**：
- 同步按钮点击后禁用，直到请求完成
- 使用 debounce（300ms）防止重复点击

**后端**：
- 同步操作使用数据库事务
- MD 文件读写使用文件锁（可选，高并发场景）

## 9. 注意事项

1. **数据源唯一性**：任务池数据始终从 `todo_list` 表获取，不单独存储
2. **MD 无删除权**：用户在 MD 中删除任务不会删除数据库记录，只是不再同步状态
3. **系统展示区**：每次同步/完成任务时自动重新生成，用户修改无效
4. **锚点不可变**：一旦生成，`source_anchor_id` 不应修改，用于双向同步匹配
5. **树形结构**：通过 `parent_id` 实现，前端递归构建，无层级限制
6. **回写条件**：必须同时满足锚点存在 + `[ ]` 存在才回写
