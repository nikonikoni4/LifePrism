# GoalsV2 界面 Todo 完成逻辑审查报告

## 一、在不同地方勾选计划（完成计划），其他地方的变化

### 当前架构

所有视图共享同一个 `TaskPoolProvider` 上下文（`useTaskPoolStore.ts:42-195`），状态存储在 `tasks` 数组中。

### 完成任务的数据流

```
用户点击完成 → updateTask(id, { state: 'completed' })
    ↓
taskPoolApi.updateTodo(id, { state: 'completed' })  [taskPool.ts:97-121]
    ↓
PUT /api/v2/todos/{id}
    ↓
taskpool_service.update_todo_with_writeback()  [taskpool_service.py:407-459]
    ├── 自动设置 actual_finished_at = 当前日期  [line 431-432]
    ├── 更新数据库
    └── 如果关联计划书且有锚点 → 回写 MD 文件 [ ] → [x]  [line 448-449]
    ↓
返回更新后的 item
    ↓
setTasks(prev => prev.map(...))  [useTaskPoolStore.ts:128]
    ↓
所有使用 useTaskPoolStore 的组件自动重新渲染
```

### 各视图的响应

| 视图 | 响应方式 | 代码位置 |
|------|----------|----------|
| **DailyTaskView** | 通过 `tasks` 状态自动更新，任务显示为已完成 | `DailyTaskView.tsx:306` |
| **TaskPoolView** | 通过 `tasks` 状态自动更新，任务显示绿色边框 | `TaskPoolView.tsx:169` |
| **CalendarView (DateGrid)** | 通过 `tasks` 状态自动更新，状态指示器变绿 | `DateGrid.tsx:32, 205` |

### 问题发现

1. **状态同步是即时的**：因为所有视图共享同一个 Context，一处修改会立即反映到所有视图。

2. **MD 回写是单向的**：完成任务时会回写 MD（`[ ]` → `[x]`），但**取消完成不会回写**：
   ```python
   # taskpool_service.py:433-435
   elif updates.get('state') in ['pool', 'scheduled'] and existing.get('state') == 'completed':
       # 不允许取消完成（根据需求文档）
       pass  # 保持 completed 状态
   ```
   **注意**：这里代码注释说"不允许取消完成"，但实际上只是不回写 MD，数据库状态仍然会被更新。

## 三、计划书视图 (PlanDocListView) 详细逻辑

### 架构概述

计划书视图使用**独立的数据存储**，与任务池视图的数据流分离：

```
PlanDocProvider (usePlanDocStore.ts)
    │
    ├── planDocs: PlanDoc[]  ← 计划书列表（不含完整内容）
    │
    ├── fetchPlanDocs()   ← GET /api/v2/goal/plan-docs
    ├── addPlanDoc()      ← POST /api/v2/goal/plan-docs
    ├── updatePlanDoc()   ← PATCH /api/v2/goal/plan-docs/{id}
    └── deletePlanDoc()   ← DELETE /api/v2/goal/plan-docs/{id}
```

### 计划书内容加载

计划书列表只包含元数据，完整内容需要单独加载：


### 保存机制

**1. 手动保存** (`line 118-133`)
```typescript
const handleSave = async () => {
    await planDocApi.updatePlanDoc(selectedDoc.id, { content: localContent });
    // PATCH /api/v2/goal/plan-docs/{id} { content: "..." }

```

**2. 自动保存（切换文档时）** (`line 95-112`)

### 计划书与任务池的数据同步

**关键点**：计划书视图中编辑 Todo（`- [ ]` / `- [x]`）**不会自动同步**到任务池。

```
用户在计划书中编辑 MD
    ↓
点击保存 → 更新 MD 文件
    ↓
（此时任务池数据未变化）
    ↓
用户切换到任务池视图，点击"同步"按钮
    ↓
POST /api/v2/taskpool/sync { plan_doc_id }
    ↓
后端解析 MD，同步到数据库
    ↓
前端刷新任务池数据
```

### 问题发现

**1. 双向同步不完整**

| 操作位置 | 操作 | MD 文件 | 数据库 |
|----------|------|---------|--------|
| 计划书视图 | 编辑 `- [ ]` → `- [x]` | ✅ 更新 | ❌ 不更新（需手动同步） |
| 任务池视图 | 点击完成任务 | ✅ 回写 | ✅ 更新 |
| 计划书视图 | 删除任务行 | ✅ 更新 | ❌ 不更新（需手动同步） |
| 任务池视图 | 删除任务 | ❌ 不更新 | ✅ 更新 |

**2. 内容编辑与元数据分离**

`usePlanDocStore.updatePlanDoc` 只同步元数据（status），不同步 content：
```typescript
// usePlanDocStore.ts:52-54
await planDocApi.updatePlanDoc(updatedDoc.id, {
    status: updatedDoc.status  // 只有 status，没有 content
}, newId);
```

内容保存在 `PlanDocListView` 中单独处理：
```typescript
// PlanDocListView.tsx:122
await planDocApi.updatePlanDoc(selectedDoc.id, { content: localContent });
```

**3. 乐观更新问题**

`usePlanDocStore.ts:48-49`:
```typescript
// Optimistic update
setPlanDocs(prev => prev.map(d => d.id === updatedDoc.id ? updatedDoc : d));
```
但失败时没有回滚逻辑（只是 `throw err`）。

**4. 计划书删除不清理关联任务**

删除计划书时，关联的任务（`plan_doc_id` 指向该计划书）不会被清理：
```typescript
// usePlanDocStore.ts:70-84
const deletePlanDoc = async (id: string) => {
    const success = await planDocApi.deletePlanDoc(id);
    if (success) {
        setPlanDocs(prev => prev.filter(d => d.id !== id));
        // 没有清理关联任务的逻辑
    }
};
```

**1. 读取 MD 文件**

**2. 解析 todoblock**
```markdown
<!-- lp:todoblock -->
- [ ] 任务1 <!-- lp:t-abc12345 -->
  - [ ] 子任务1.1 <!-- lp:t-def67890 -->
- [x] 任务2 <!-- lp:t-ghi11111 -->

```

**3. 为无锚点的任务生成锚点** (`line 286-296`)
```python
if not task['anchor_id']:
    new_anchor = _generate_anchor_id()  # t-{uuid[:8]}
    task['anchor_id'] = new_anchor
    # 构建新行并写回 MD
```

**4. 数据库同步逻辑** (`line 318-390`)

| 情况 | 处理方式 |
|------|----------|
| MD 中有锚点，DB 中存在 | 更新 content、pool_order_index |
| MD 中有锚点，DB 中不存在 | 创建新任务 |
| MD 中 `[x]`，DB 中非 completed | 更新为 completed |
| MD 中 `[ ]`，DB 中 completed | **不处理**（不会取消完成） |

**5. 更新系统展示区** (`line 393-394`)
```python

```

## 五、删除 Todo 后其他地方的变化

### 删除流程

```
用户点击删除 → deleteTask(id)  [useTaskPoolStore.ts:144-153]
    ↓
taskPoolApi.deleteTodo(id)  [taskPool.ts:155-163]
    ↓
DELETE /api/v2/todos/{id}
    ↓
taskpool_service.delete_todo(todo_id)  [taskpool_service.py:699-709]
    ↓
todo_provider.delete_todo(todo_id)  [数据库删除]
    ↓
setTasks(prev => prev.filter(t => t.id !== id))  [前端状态更新]
```

### 各视图响应

由于共享 `TaskPoolProvider`，删除后：
- **DailyTaskView**: 任务从列表中消失
- **TaskPoolView**: 任务从列表中消失
- **CalendarView**: 任务从日期卡片中消失

### 问题发现

**1. 子任务处理问题**

当前代码**没有级联删除子任务**。如果删除父任务：
- 数据库中子任务的 `parent_id` 仍然指向已删除的父任务 ID
- 前端 `buildTaskTree` 会将这些"孤儿"子任务作为根节点显示：
  ```typescript
  // DailyTaskView.tsx:36-38
  if (parent) {
      parent.children.push(taskWithChildren);
  } else {
      // 父任务不在当前列表中，作为根节点
      roots.push(taskWithChildren);
  }
  ```

**2. MD 文件不同步**

删除任务时**不会更新 MD 文件**。如果任务来自计划书：
- 数据库中任务被删除
- MD 文件中的任务行仍然存在
- 下次同步时会重新创建该任务

## 六、其他潜在问题

### 1. 乐观更新与错误处理不一致

`useTaskPoolStore.ts:129-140`:
```typescript
try {
    const response = await taskPoolApi.updateTodo(id, apiUpdates);
    const updatedItem = mapBackendTaskItemToFrontend(response.item);
    setTasks(prev => prev.map(t => t.id === id ? { ...t, ...updatedItem } : t));
} catch (err) {
    // 失败时仍然更新本地状态（应该是回滚）
    setTasks(prev => prev.map(t => t.id === id ? { ...t, ...updates } : t));
}
```
**问题**：catch 块中应该回滚到原始状态，而不是应用更新。

### 2. 状态转换逻辑分散

状态转换逻辑分布在多处：
- 前端 `useTaskPoolStore.ts:161-163` (scheduleTask 设置 date 时改 state)
- 后端 `taskpool_service.py:668-669` (create_todo_v2 设置 date 时改 state)
- 后端 `todos_api.py` (update_todo 设置 date 时改 state)

**建议**：统一在后端处理状态转换逻辑。

### 3. CalendarView 缺少完成功能

`DateGrid.tsx` 只显示任务，不支持直接完成。用户需要：
1. 点击日期卡片 → 设置 selectedDate
2. 切换到 DailyTaskView 查看该日期任务
3. 在 DailyTaskView 中完成任务

**用户体验问题**：无法在日历视图中快速完成任务。

### 4. 任务池初始加载

`useTaskPoolStore.ts:171-173`:
```typescript
useEffect(() => {
    loadTasks();  // 无参数，加载所有任务
}, [loadTasks]);
```
**问题**：初始加载所有任务，数据量大时可能影响性能。

### 5. 取消完成的行为不明确

代码注释说"不允许取消完成"，但实际上：
- 数据库状态**可以**被更新（从 completed 改为其他状态）
- MD 文件**不会**被回写（`[x]` 不会变回 `[ ]`）

这会导致数据库和 MD 文件状态不一致。

## 七、同源架构性能问题与解决方案

### 问题描述

当前所有视图共享 `TaskPoolProvider`，一次性加载全部 Todo 数据：

```typescript
// useTaskPoolStore.ts:171-173
useEffect(() => {
    loadTasks();  // 无参数，加载所有任务
}, [loadTasks]);
```

**潜在风险**：
- 当 Todo 数量达到几百个时，TaskPoolView 无筛选状态下渲染性能下降
- 初始加载时间随数据量线性增长
- 内存占用增加

### 解决方案对比

| 方案 | 复杂度 | 适用场景 | 对现有问题的影响 |
|------|--------|----------|------------------|
| **虚拟滚动 + 默认筛选** | 低 | 500-2000 条 | 无影响 |
| 分页加载 | 中 | 2000+ 条 | 增加复杂性 |
| 按需加载 + 本地缓存 | 高 | 10000+ 条 | 大幅增加复杂性 |

### 推荐方案：虚拟滚动 + 默认筛选

**1. 虚拟滚动**

使用 `@tanstack/react-virtual` 只渲染可见区域：

```typescript
import { useVirtualizer } from '@tanstack/react-virtual';

const virtualizer = useVirtualizer({
  count: filteredTasks.length,
  getScrollElement: () => parentRef.current,
  estimateSize: () => 60,  // 每个任务项高度
});
```

**效果**：即使有 1000 个任务，DOM 中也只有 20-30 个节点

**2. 默认筛选策略**

TaskPoolView 初始不显示全部，默认筛选 `pool` 状态：

```typescript
const [filter, setFilter] = useState<TaskState>('pool');
```

### 架构变更影响分析

如果改为分页/按需加载架构，对现有问题的影响：

| 现有问题 | 保持同源 + 虚拟滚动 | 改为分页/按需加载 |
|----------|---------------------|-------------------|
| 删除任务不更新 MD 文件 | 无影响 | 无影响 |
| 取消完成不回写 MD | 无影响 | 无影响 |
| 计划书编辑 Todo 不自动同步 | 无影响 | 无影响 |
| 删除计划书不清理关联任务 | 无影响 | 无影响 |
| 删除父任务不级联删除子任务 | 无影响 | **复杂化** - 子任务可能不在当前加载范围 |
| 乐观更新错误处理 | 无影响 | **更复杂** - 需要处理缓存失效 |
| CalendarView 无法完成任务 | 无影响 | 无影响 |
| 状态转换逻辑分散 | 无影响 | 无影响 |

**结论**：大部分问题是后端逻辑问题，与前端数据加载架构无关。改为分页架构会引入新的复杂性（缓存同步、跨页数据一致性），收益不明显。

## 八、Todo ID 格式问题

### 问题描述

当前 Todo 使用数据库自增 `int` 类型作为 ID，而其他实体使用前缀格式：

| 实体 | ID 格式 | 类型 |
|------|---------|------|
| Goal | `goal-xxx` | `string` |
| PlanDoc | `planDoc-xxx` | `string` |
| **Todo** | `123` | `int` |

这导致：
1. **类型不一致**：前端需要处理混合类型（`number` vs `string`）
2. **锚点冗余**：需要额外的 `source_anchor_id` 字段关联 MD 锚点
3. **可读性差**：调试时 `123` 无法一眼看出是什么类型的数据

### 方案对比

| 维度 | 自增 ID (int) | 前缀 ID (todo-xxx) |
|------|---------------|-------------------|
| **生成方式** | 数据库自动生成 | 代码生成 UUID |
| **可读性** | 差（`123`） | 好（`todo-a1b2c3d4`） |
| **调试友好** | 差 | 好（一眼看出类型） |
| **前端处理** | 需要 `number` 类型 | 统一 `string` 类型 |
| **与其他实体一致性** | 不一致 | 一致 |
| **MD 锚点关联** | 需要额外字段 | 可直接用 ID 作为锚点 |
| **迁移成本** | 无 | 高 |

### 如果改为 todo-xxx 格式

**生成方式**：
```python
import uuid

def generate_todo_id() -> str:
    return f"todo-{uuid.uuid4().hex[:8]}"
```

**数据库改动**：
```sql
-- 改为 TEXT 主键
CREATE TABLE todo_list (
    id TEXT PRIMARY KEY,  -- 原为 INTEGER PRIMARY KEY AUTOINCREMENT
    ...
)
```

**迁移成本估算**：

| 改动点 | 工作量 |
|--------|--------|
| 数据库 schema | 改 `id` 类型 + 数据迁移脚本 |
| `todo_provider.py` | ~20 处 `int` → `str` |
| `taskpool_service.py` | ~15 处 |
| `todos_api.py` / `taskpool_api.py` | ~10 处 |
| 前端 `types.ts` | ~5 处 |
| 前端 API 调用 | ~10 处 |
| **总计** | **约 60 处改动 + 数据迁移** |

### 建议

- **短期**：保持现状，当前方案可用，不是阻塞性问题
- **长期**：如果系统还在早期开发阶段且数据量小，可考虑统一改为 `todo-xxx` 格式
- **收益**：统一 ID 格式后，可以简化锚点逻辑（直接用 `todo-xxx` 作为 MD 锚点，去掉 `source_anchor_id` 字段）

| 数据一致性 | 删除计划书不清理关联任务 | 中 |
| 数据完整性 | 删除父任务不级联删除子任务 | 中 |
| 性能 | 大量 Todo 时渲染性能下降 | 中 |
| 代码质量 | 乐观更新错误处理逻辑错误（TaskPool 和 PlanDoc） | 低 |
| 用户体验 | CalendarView 无法直接完成任务 | 低 |
| 架构 | 状态转换逻辑分散 | 低 |
| 架构 | 计划书内容与元数据保存逻辑分离 | 低 |

### 修复优先级建议

**高优先级（先修）：**
- 虚拟滚动（解决性能）
- 默认筛选（减少初始渲染量）
- 后端级联删除子任务

**中优先级：**
- 删除任务回写 MD
- 乐观更新回滚逻辑

**低优先级（可接受现状）：**
- 计划书自动同步（手动同步是合理的设计）
- CalendarView 完成功能
